## 2. 模块 2：播放量计数（Redis 增量 + 定时落库）

### 为什么不用数据库直接 +1？
每次播放都 `UPDATE video SET play_count = play_count + 1`，高并发下数据库是瓶颈。Redis 单线程 + 内存，`INCR` 是原子操作，扛得住。

### 架构：增量模式

```
播放请求 ──▶ Redis INCR video:play:{id}   （毫秒级，实时）
                 │
                 ▼ 每 5 分钟 @Scheduled
        GETDEL 取出增量 → UPDATE video SET play_count = play_count + 增量
```

### 三个关键点

**① 播放接口**（[VideoServiceImpl.recordPlay](file:///d:/git/practice/practice2/backend/src/main/java/com/example/practice/service/impl/VideoServiceImpl.java)）：
```java
// Redis 原子自增（高并发不丢）
stringRedisTemplate.opsForValue().increment(KEY_PLAY + videoId);
// 登录用户顺便记录观看历史（同一视频只留一条，重复看更新时间）
// 唯一约束冲突用 try-catch DuplicateKeyException 转更新
```

**② 定时落库**（[CountSyncTask.java](file:///d:/git/practice/practice2/backend/src/main/java/com/example/practice/task/CountSyncTask.java)）：
```java
@Scheduled(fixedRate = 300_000)   // 每 5 分钟
public void syncCounts() { ... }
// GETDEL：取出增量并删除，保证同一增量只落库一次（原子操作）
String delta = stringRedisTemplate.opsForValue().getAndDelete(key);
```
> 需要在启动类加 `@EnableScheduling` 才能启用定时任务。

**③ 详情页展示准实时播放量**：数据库值 + Redis 未落库增量：
```java
String inc = stringRedisTemplate.opsForValue().get(KEY_PLAY + id);
if (inc != null) vo.setPlayCount(video.getPlayCount() + Integer.parseInt(inc));
```

**权衡**：Redis 崩溃最多丢 5 分钟增量数据，业务可接受；换来的是播放接口完全不打数据库。

## 3. 模块 3：互动体系

### 3.1 点赞：Redis Set 去重（为什么点赞用 Redis？）

点赞有两个需求：**计数** + **当前用户是否点过**。两者都要频繁查询，放 Redis 最合适：

```java
// Set 记录"谁点过赞"：isMember 查状态，SADD/SREM 切换
boolean liked = isMember(KEY_LIKE + videoId, userId);
if (liked) {
    opsForSet().remove(KEY_LIKE + videoId, userId);   // 取消
    opsForValue().decrement(KEY_LIKE_COUNT + videoId);
} else {
    opsForSet().add(KEY_LIKE + videoId, userId);      // 点赞
    opsForValue().increment(KEY_LIKE_COUNT + videoId);
}
```
> Redis Set 天然去重：同一用户点 100 次，集合里只有一个元素。

### 3.2 收藏：数据库关系表（为什么收藏用数据库？）

收藏是"用户-视频"关系，要长期保存、要分页查询、要能确认唯一性。用一张**关系表** + **unique 约束**：

```java
// video_favorite 表 (video_id, user_id) 有唯一约束
// 插入成功 = 收藏；违反唯一约束（先查再判断） = 已存在 → 删除 = 取消收藏
if (exist == null) {
    favoriteMapper.insert(f);
    changeVideoCount(videoId, "favorite_count", +1);
} else {
    favoriteMapper.deleteById(exist.getId());
    changeVideoCount(videoId, "favorite_count", -1);
}
```

**点赞 vs 收藏的设计对比**（面试常问）：
| | 点赞 | 收藏 |
|---|---|---|
| 存哪 | Redis（内存） | MySQL（磁盘，持久） |
| 为什么 | 高频、要查状态、可容忍丢失 | 重要关系、要分页查询、必须持久 |
| 去重手段 | Set 天然去重 | unique 约束 |

### 3.3 投币：每日限额 3 枚

```java
// 每天 0 点重置：查询"今天"的投币记录总数
Long todayCoins = coinMapper.selectCount(wrapper
        .eq(userId).ge(createTime, LocalDate.now().atStartOfDay()));
if (todayCoins + coin > 3) throw new BusinessException("今日投币已达上限");
// 落一条投币记录 + 视频 coin_count 累加
```

### 3.4 评论：楼中楼自关联表（核心设计）

**表结构**（[video_comment](file:///d:/git/practice/practice2/backend/src/main/java/com/example/practice/entity/VideoComment.java)）：
```sql
video_comment(id, video_id, user_id, content, parent_id, root_id, create_time)
```
- `parent_id`：回复的是谁（0 = 一级评论）
- `root_id`：属于哪条一级评论（楼中楼的"楼"）

**查询策略（两步查，避免 N+1）**：
```java
// 第一步：一级评论分页
Page<VideoComment> rootPage = selectPage(page, size, parent_id = 0);
// 第二步：一次性查出所有回复（root_id IN 一级评论id）
List<VideoComment> replies = selectList(video_id = X AND root_id IN (rootIds));
// 第三步：按 rootId 分组，挂到对应一级评论下
```

**发表评论时回填 root_id**：
```java
commentMapper.insert(comment);          // 插入后 id 回填
if (parentId == 0) {
    comment.setRootId(comment.getId()); // 一级评论：自己就是根
} else {
    comment.setRootId(parent.getRootId() == 0 ? parent.getId() : parent.getRootId());
}
commentMapper.updateById(comment);
```

## 6. 开发路线（为什么这个顺序）

```
① 建互动表（评论/收藏/历史/投币）      ← 数据模型先行
② 造规范测试数据（test-data.sql）     ← 有了数据才能测
③ 模块2 播放计数（独立、最简）        ← 先体验 Redis 增量 + 定时任务
④ 模块3 互动（点赞→收藏→投币→评论）   ← 从简到繁，评论楼中楼最后（最复杂）
⑤ 模块5 个人中心（查询数据）          ← 依赖③④产生的关系数据
⑥ 模块6 首页（展示数据）              ← 所有功能的数据汇合点
```

**为什么先测试数据后写功能？** 真实开发里表结构和数据会反哺接口设计——写 SQL 时发现"评论需要 parent_id 和 root_id 两个字段"，这个结论直接影响后面的查询代码。

## 7. 踩坑记录（本批次真实遇到）

### 坑 1：增量编译导致 `NoClassDefFoundError: CommentDTO`
- **现象**：`mvn spring-boot:run` 启动报错找不到新写的类，但 `mvn compile` 显示成功。
- **原因**：第一次编译失败后 `target/classes` 留下不一致的 class 文件，增量编译没有清理。
- **解决**：`mvn clean compile` 后重启。
- **教训**：**改动的类较多时，编译失败后先 `clean` 再编译**，别信增量编译。

### 坑 2：PowerShell 里 curl 发中文 JSON 报 500
- **现象**：接口测试时 `curl -d $json` 发送中文评论报"系统繁忙"。
- **原因**：PowerShell 传给 curl 的中文编码不是 UTF-8，后端 JSON 解析失败。
- **解决**：改用 `Invoke-RestMethod`（自动处理 UTF-8）或给 curl 显式 UTF-8 字节。
- **教训**：**这是测试工具问题，不是代码 bug**——定位问题时要区分"接口坏了"和"请求没发对"。

### 坑 3：`computed` 忘导入导致页面白屏
- **现象**：浏览器打开首页空白，控制台 `ReferenceError: computed is not defined`。
- **原因**：`<script setup>` 里用了 `computed` 但 import 里漏了。
- **解决**：补全 import。
- **教训**：**Vue 组合式 API 每个函数都要显式 import**，不像选项式 API 全局可用。

## 9. 一句话总结

> **四个模块的本质都是"数据处理"**：播放量是"高频计数"（Redis 增量+定时落库），点赞是"集合关系"（Redis Set），收藏/历史是"持久关系"（数据库关系表），评论是"树形结构"（parent_id + root_id 自关联）。**先分清数据的特点，再决定存哪、怎么存——这是后端设计的核心能力。**
