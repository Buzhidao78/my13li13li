# 会员订单功能从 0 到 1 开发指南

> 配套练习：登录系统（《登录功能从0到1开发指南.md》）
> 本文档讲解"会员充值订单"功能（Redis + RabbitMQ 练习）如何从 0 到 1 写出来：
> **先写什么、后写什么、为什么这个顺序**，前后端代码全部覆盖。

---

## 0. 功能总览：我们要做一个什么？

**业务故事**：用户在充值页选择会员等级（白银/黄金/钻石）→ 点击下单 → 模拟支付 → 支付成功后**异步**升级会员。如果不支付，30 秒后订单自动关闭。

**技术考点**（这是本次练习的核心，所有代码都围绕这两句话展开）：

| 中间件 | 考点 | 通俗解释 |
|---|---|---|
| Redis | 1. 分布式锁防重复下单 | 同一用户疯狂连点，只让一次请求通过 |
| Redis | 2. 订单信息缓存 | 查订单先查缓存，减轻 MySQL 压力 |
| Redis | 3. MQ 消费幂等 | 同一条消息被消费两次，会员只升级一次 |
| RabbitMQ | 1. Direct 交换机 + 死信交换机 DLX + 队列绑定 | 消息按路由键精确投递；过期的消息转投死信 |
| RabbitMQ | 2. 消息可靠性（confirm + 持久化 + 手动 ACK） | 保证消息"不丢" |
| RabbitMQ | 3. TTL 过期 + 死信队列 → 延时关闭订单 | 不用定时任务，用消息实现"30 秒后关单" |
| RabbitMQ | 4. 消息重复消费 + 业务幂等 | 消费端去重 |
| RabbitMQ | 5. 模拟异常：消费者报错 → 消息重回队列 | 失败自动重试 |

**一句话记住整个流程**：

```
下单 →(Redis 锁防重 + 订单写库 + 写缓存 + 发 TTL 延时消息)
     →(不支付 30 秒后 TTL 到期 → 死信队列 → 自动关单)
     →(模拟支付 → 置已支付 + 发"会员升级"消息)
     →(消费者手动 ACK + 幂等判断 → 升级会员)
```

## 1. 第 0 步：先想清楚数据模型（数据库设计）

> **为什么数据库排第一？** 一切代码都建立在数据之上。实体类、Mapper、业务逻辑、接口返回，全都围着表转。表结构没想清楚，后面的代码全都要返工。

### 1.1 订单表 `member_order`

订单是"买东西"的记录，字段怎么设计？想象一张**超市小票**：

- 订单号（给用户看的编号）→ `order_id`
- 谁买的 → `user_id`
- 买了什么 → `level`（等级）+ `amount`（金额）+ `days`（时长）
- 买到什么程度 → `status`（状态机！）+ `pay_time`（付款时间）+ `close_time`（关闭时间）

关键字段解释：

```sql
CREATE TABLE IF NOT EXISTS member_order (
    id          BIGINT        NOT NULL AUTO_INCREMENT COMMENT '主键',
    order_id    VARCHAR(32)   NOT NULL COMMENT '业务订单号（全局唯一，Redis 幂等和 MQ 消息都以它为准）',
    user_id     BIGINT        NOT NULL COMMENT '下单用户 id',
    level       TINYINT       NOT NULL COMMENT '购买的会员等级 1-白银 2-黄金 3-钻石',
    amount      DECIMAL(10,2) NOT NULL COMMENT '订单金额（元）',
    days        INT           NOT NULL COMMENT '会员时长（天）',
    status      TINYINT       NOT NULL DEFAULT 0 COMMENT '订单状态 0-待支付 1-已支付 2-已关闭 3-已过期(延时关单)',
    create_time DATETIME      DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    pay_time    DATETIME      DEFAULT NULL COMMENT '支付时间',
    close_time  DATETIME      DEFAULT NULL COMMENT '关闭/过期时间',
    update_time DATETIME      DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (id),
    UNIQUE KEY uk_order_id (order_id),   -- 订单号唯一：业务幂等的"地基"
    KEY idx_user_id (user_id)            -- 按用户查订单的索引
) ENGINE = InnoDB COMMENT = '会员充值订单表';
```

**一个关键设计**：`order_id` 是**业务订单号**（不是自增主键 `id`），因为：

- MQ 消息、Redis 幂等标记、缓存 key **都用 `order_id` 关联**，它是整个链路的"身份证"
- 自增 `id` 是数据库内部编号，不能暴露给业务

### 1.2 用户表加会员字段

会员是"用户的属性"，所以给 `user` 表加两个字段：

```sql
ALTER TABLE `user`
    ADD COLUMN member_level TINYINT NOT NULL DEFAULT 0 COMMENT '会员等级 0-普通 1-白银 2-黄金 3-钻石' AFTER `sign`,
    ADD COLUMN member_expire DATETIME DEFAULT NULL COMMENT '会员到期时间（NULL 表示从未开通）' AFTER `member_level`;
```

> 注意：已存在的表用 `ALTER TABLE` 加字段，新建的表直接写在 `CREATE TABLE` 里。`schema.sql` 里两种都保留了，方便不同阶段执行。

## 2. 后端开发顺序（核心思想：按"依赖倒序"）

> **为什么按这个顺序？** 请想象盖房子：先打地基（依赖），再砌墙（业务），最后装修（接口/前端）。**每一层都只依赖它下面的层**，从下往上写，每写完一层它就能编译、能测试，心里不慌。

```
① 依赖与配置         pom.xml + application.yml
② 常量               MemberLevel + RabbitConstants
③ 实体 + Mapper      MemberOrder + MemberOrderMapper
④ DTO / VO           入参 / 出参
⑤ RabbitMQ 配置      RabbitMQConfig（交换机/队列/绑定）
⑥ 业务逻辑           OrderService / OrderServiceImpl（核心！）
⑦ 消费者             OrderListener（MQ 监听器）
⑧ 控制器             OrderController + MemberController
```

### 第 1 步：依赖与配置（地基）

**pom.xml** 加两个依赖：`spring-boot-starter-data-redis`（Redis）和 `spring-boot-starter-amqp`（RabbitMQ）。

**application.yml** 关键配置，每个配置都是考点：

```yaml
spring:
  rabbitmq:
    host: localhost
    port: 5672
    username: guest
    password: guest
    # 生产者 confirm：消息投递到交换机后回调确认（可靠投递第 1 道保险）
    publisher-confirm-type: correlated
    # 生产者 return：消息路由不到队列时回调（可靠投递第 2 道保险）
    publisher-returns: true
    listener:
      simple:
        # 手动 ACK：处理成功才确认；失败可重回队列，保证消息不丢
        acknowledge-mode: manual
        prefetch: 1          # 单消费者一次拉 1 条，方便观察日志
order:
  ttl-ms: 30000              # 未支付订单自动关闭延时：30 秒，方便观察
```

> **类比**：`confirm` 像快递的"签收回执"（东西送没送到，你心里有数）；`manual ACK` 像你自己验货后才签字（验出问题就退回重发）。

### 第 2 步：常量（把"魔法数字/字符串"关起来）

**为什么要有常量？** 交换机名、队列名、路由键、Redis key 前缀，这些字符串拼错一个字母，整个链路静默失败且极难排查。**统一放一个类里，一处定义，到处引用。**

`RabbitConstants.java`（挑重点）：

```java
public class RabbitConstants {
    // ===== 会员升级（Direct 直连交换机）=====
    public static final String EX_MEMBER = "member.exchange";
    public static final String Q_MEMBER_UPGRADE = "member.upgrade.queue";
    public static final String RK_MEMBER_UPGRADE = "member.upgrade";

    // ===== 延时关单（TTL + 死信交换机 DLX）=====
    public static final String EX_ORDER_TTL = "order.ttl.exchange";
    public static final String Q_ORDER_TTL = "order.ttl.queue";
    public static final String RK_ORDER_CREATE = "order.create";
    public static final String EX_ORDER_DLX = "order.dlx.exchange";
    public static final String Q_ORDER_CLOSE = "order.close.queue";
    public static final String RK_ORDER_CLOSE = "order.close";

    // ===== Redis key 统一前缀 =====
    public static final String LOCK_ORDER_PREFIX = "order:lock:";   // 分布式锁
    public static final String CACHE_ORDER_PREFIX = "order:";       // 订单缓存
    public static final String IDEMPOTENT_PREFIX = "processed:";    // 消费幂等标记
    public static final String RETRY_PREFIX = "retry:";             // 消费重试次数
}
```

`MemberLevel.java`：会员等级信息（名称/价格/天数）统一维护，前端需要时通过接口获取：

```java
public class MemberLevel {
    public static final int NORMAL = 0, SILVER = 1, GOLD = 2, DIAMOND = 3;
    // Info 类：level / name / amount / days / remark
    public static boolean isValid(int level) {   // 只允许买 白银/黄金/钻石
        return level >= SILVER && level <= DIAMOND;
    }
}
```

> **为什么等级用常量而不是数据库表？** 练习项目等级固定不变，写死在常量里最简单；生产环境等级经常变，才考虑放数据库/配置中心。**先简单，后复杂。**

### 第 3 步：实体 + Mapper（把表和 Java 对象对应起来）

`MemberOrder.java`：`@TableName("member_order")` 告诉 MyBatis-Plus 这张表对应哪个类，字段自动驼峰映射（`create_time` → `createTime`，靠配置里 `map-underscore-to-camel-case`）。

`MemberOrderMapper.java`：空接口继承 `BaseMapper<MemberOrder>`，**一行 SQL 都不用写**，就拥有增删改查。

> **为什么实体先于业务？** 业务代码到处要用 `MemberOrder`，它不存在，业务层写不了。所以实体/常量/配置这类"被依赖的底层"必须先就位。

---

### 第 4 步：DTO / VO（入参出参分开，前后端解耦）

**三个原则，用类比理解：**

- **DTO**（入参）：前端传什么，只留必要的。下单只需要 `level`，所以 `CreateOrderDTO` 只有一个字段。**不要直接把实体当入参**，否则前端能乱传 `userId`、`status`。
- **VO**（出参）：前端要什么，就返回什么。`MemberOrderVO` 把 `status` 数字翻译成 `statusText`（0→待支付…），把 `level` 翻译成 `levelName`。**实体里的字段 ≠ 前端能看到的字段**。
- **MQ 消息体** `UpgradeMessage`：不是给前端用的，是**两个进程（生产者和消费者）之间的"快递单"**。它必须能序列化成 JSON 传过 RabbitMQ，所以字段要简单、可序列化。

```java
// MQ 消息体：支付成功后通知"会员升级"的内容
@Data
public class UpgradeMessage {
    private String orderId;       // 幂等判断就用它
    private Long userId;
    private Integer level;        // 买的等级
    private Integer days;         // 时长
    private Boolean simulateError; // 演示开关：true 时消费者故意报错
}
```

> **为什么分 DTO/VO？** 前端传的和后端给的，往往不是同一份数据。入参收窄（安全）、出参裁剪（隐私 + 友好），这就是"分层"的意义。

### 第 5 步：RabbitMQ 配置（核心！交换机/队列/绑定一次声明）

这是 RabbitMQ 练习的主战场。`RabbitMQConfig.java` 负责把**交换机、队列、绑定关系**一次性声明好，应用启动时就自动创建。

**5.1 消息转换器 + 可靠投递回调**

```java
@Bean
public MessageConverter messageConverter() {
    return new Jackson2JsonMessageConverter();  // 对象 <-> JSON
}

@Bean
public RabbitTemplate rabbitTemplate(ConnectionFactory cf, MessageConverter mc) {
    RabbitTemplate t = new RabbitTemplate(cf);
    t.setMessageConverter(mc);
    t.setMandatory(true);   // 路由不到队列时触发 return 回调，而不是静默丢弃
    // confirm：消息是否到交换机
    t.setConfirmCallback((correlationData, ack, cause) -> {
        if (ack) log.info("confirm 成功：已投递到交换机, id={}", correlationData.getId());
        else     log.error("confirm 失败：原因={}", cause);
    });
    // return：消息是否路由到队列
    t.setReturnsCallback(returned -> log.error("return 路由失败：exchange={}, rk={}", ...));
    return t;
}
```

> 这两段回调就是"可靠投递"的**眼睛**——之前 MQ 宕机时，你靠它们在日志里看到"confirm 失败"，从而发现问题。

**5.2 会员升级：Direct 交换机**

```java
@Bean public DirectExchange memberExchange() { return new DirectExchange(RabbitConstants.EX_MEMBER, true, false); }
@Bean public Queue memberUpgradeQueue()       { return new Queue(RabbitConstants.Q_MEMBER_UPGRADE, true); }
@Bean public Binding memberUpgradeBinding() {
    return BindingBuilder.bind(memberUpgradeQueue())
            .to(memberExchange())
            .with(RabbitConstants.RK_MEMBER_UPGRADE);  // 按路由键精确匹配
}
```

> **Direct 交换机类比**：像快递站的"分拣口"，只认"地址标签"（路由键）完全匹配的件。`member.upgrade` 这个标签只送进会员升级队列。

**5.3 延时关单：TTL 队列 + 死信交换机（本练习的精华）**

```java
// TTL 队列：消息在这里"躺"到过期，过期后按配置转投死信
@Bean
public Queue orderTtlQueue() {
    Map<String, Object> args = new HashMap<>();
    args.put("x-dead-letter-exchange", RabbitConstants.EX_ORDER_DLX);       // 死了去哪
    args.put("x-dead-letter-routing-key", RabbitConstants.RK_ORDER_CLOSE);  // 死了用什么标签
    return new Queue(RabbitConstants.Q_ORDER_TTL, true, false, false, args);
}

// 死信交换机 + 关单队列
@Bean public DirectExchange orderDlxExchange() { return new DirectExchange(RabbitConstants.EX_ORDER_DLX, true, false); }
@Bean public Queue orderCloseQueue()            { return new Queue(RabbitConstants.Q_ORDER_CLOSE, true); }
@Bean public Binding orderCloseBinding() {
    return BindingBuilder.bind(orderCloseQueue()).to(orderDlxExchange()).with(RabbitConstants.RK_ORDER_CLOSE);
}
```

> **死信机制类比**：TTL 队列像"候机厅"，消息在候机厅等 30 秒（TTL），到点了**还没被取走**，系统自动把它改签到"死信航线"，飞到关单队列。这个机制**完全由 RabbitMQ 实现，不用我们写任何定时器**。

**为什么持久化（durable=true）？** MQ 重启后，队列和消息还在——这是"消息不丢"的底层保障之一。

### 第 6 步：业务逻辑（核心中的核心）

`OrderServiceImpl` 是**所有考点汇聚的地方**。按方法拆开讲，每个方法对应一个考点。

**6.1 下单：Redis 分布式锁 + 订单缓存 + TTL 延时消息**

```java
public MemberOrderVO createOrder(Long userId, Integer level) {
    // 1. 校验等级
    if (level == null || !MemberLevel.isValid(level)) throw new BusinessException("会员等级不合法");

    // 2. Redis 分布式锁：防重复下单
    //    setIfAbsent 是原子操作：key 不存在才设置成功并返回 true（=拿到锁）
    //    带 5 秒过期：防止程序崩了锁永远不释放（死锁）
    String lockKey = RabbitConstants.LOCK_ORDER_PREFIX + userId;
    Boolean locked = stringRedisTemplate.opsForValue()
            .setIfAbsent(lockKey, "1", Duration.ofSeconds(5));
    if (locked == null || !locked) throw new BusinessException("正在处理中，请勿重复提交");

    try {
        // 3. 双保险：库里是否已有"待支付"订单（防止锁过期后用户又点了一次）
        Long pendingCount = orderMapper.selectCount(...eq(userId).eq(status, 0));
        if (pendingCount > 0) throw new BusinessException("您有待支付的订单，请先完成支付");

        // 4. 组装订单入库（status=0 待支付）
        MemberOrder order = new MemberOrder();
        order.setOrderId(generateOrderId());
        order.setUserId(userId); order.setLevel(level);
        order.setAmount(info.amount); order.setDays(info.days);
        order.setStatus(0);
        orderMapper.insert(order);

        // 5. 订单写 Redis 缓存（读多写少，缓存明显减轻 MySQL 压力）
        cacheOrder(order);

        // 6. 发送 TTL 延时消息：消息在 TTL 队列躺 30 秒，
        //    到期自动转死信 -> 关单队列 -> 消费者关掉未支付订单
        rabbitTemplate.convertAndSend(EX_ORDER_TTL, RK_ORDER_CREATE, order.getOrderId(),
                msg -> { msg.getMessageProperties().setExpiration(String.valueOf(ttlMs)); return msg; });
        return MemberOrderVO.from(order);
    } finally {
        // 7. 无论成功失败都释放锁（finally 保证）
        stringRedisTemplate.delete(lockKey);
    }
}
```

> **分布式锁类比**：仓库只有一个"进货通道"，谁先拿到钥匙（setIfAbsent 成功）谁进去，其他人只能门口等（提示"正在处理中"）。钥匙带 5 秒自动过期，防止拿到钥匙的人中途晕倒把通道堵死。

**6.2 模拟支付：写库 + 防重复支付 + 发"会员升级"消息**

```java
public MemberOrderVO payOrder(Long userId, String orderId, boolean simulateError) {
    // 1. 查订单（写操作以库为准，不走缓存）
    MemberOrder order = orderMapper.selectOne(...eq(orderId));
    if (order == null) throw new BusinessException("订单不存在");
    if (!order.getUserId().equals(userId)) throw new BusinessException("无权操作该订单");
    if (order.getStatus() != 0) throw new BusinessException("订单状态不允许支付");

    // 2. 更新为已支付：WHERE status=0 保证并发下只有一次成功（防重复支付）
    MemberOrder update = new MemberOrder();
    update.setStatus(1); update.setPayTime(LocalDateTime.now());
    int rows = orderMapper.update(update, ...eq(id).eq(status, 0));
    if (rows == 0) throw new BusinessException("订单状态已变化，支付失败");

    // 3. 刷新缓存里的订单状态
    order.setStatus(1); order.setPayTime(update.getPayTime()); cacheOrder(order);

    // 4. 发"会员升级"MQ 消息（异步：支付成功 -> 通知消费者升级会员）
    UpgradeMessage msg = new UpgradeMessage();
    msg.setOrderId(orderId); msg.setUserId(userId);
    msg.setLevel(order.getLevel()); msg.setDays(order.getDays());
    msg.setSimulateError(simulateError);  // 演示开关
    rabbitTemplate.convertAndSend(EX_MEMBER, RK_MEMBER_UPGRADE, msg, new CorrelationData(orderId));
    return MemberOrderVO.from(order);
}
```

> **为什么支付成功后不直接改会员等级，而是发消息？** 这是**异步解耦**的核心思想：支付接口只管"收钱 + 发消息"，立刻返回。升级会员这种耗时/易错的操作交给消费者慢慢做。就算消费者挂了，消息还在队列里，**升级不会丢**。这就是 MQ 的"削峰 + 解耦 + 可靠"。

**6.3 会员升级：MQ 消费幂等（重点）**

```java
public void upgradeMember(UpgradeMessage msg) {
    String orderId = msg.getOrderId();

    // 1. 幂等判断：Redis 里已有"已处理"标记，说明这条消息处理过了，直接跳过
    //    避免消息重复投递（重试/网络抖动）导致重复给用户加会员
    String idempotentKey = RabbitConstants.IDEMPOTENT_PREFIX + orderId;
    if (Boolean.TRUE.equals(stringRedisTemplate.hasKey(idempotentKey))) {
        log.info("幂等命中：订单 {} 已处理过，跳过", orderId);
        return;
    }

    // 2. 校验订单确实已支付（防止消息伪造/提前到达）
    MemberOrder order = ...;
    if (order == null || order.getStatus() != 1) throw new BusinessException("订单未支付");

    // 3. 升级：等级取更高者，时长在原到期时间上累加（买黄金不会把钻石降级）
    LocalDateTime base = user.getMemberExpire();
    LocalDateTime newExpire = (base != null && base.isAfter(now)) ? base : now;
    newExpire = newExpire.plusDays(msg.getDays());
    int newLevel = Math.max(user.getMemberLevel() ?? 0, msg.getLevel());
    userMapper.updateById(updateUser);

    // 4. 处理成功后写幂等标记（TTL 1 天，覆盖重试窗口）
    stringRedisTemplate.opsForValue().set(idempotentKey, "1", Duration.ofDays(1));
}
```

> **幂等类比**：快递员送包裹，第一次送过会在门卫处登记（Redis 标记）。第二次再来，门卫一看"这单送过了"，直接说"不用送了"。**保证同一件事只做一次**。

**6.4 延时关单：消费死信队列**

```java
public void closeExpiredOrder(String orderId) {
    MemberOrder order = ...;                       // 查订单
    if (order == null) return;                     // 不存在直接返回（消息幂等）
    if (order.getStatus() != 0) return;            // 已支付/已关闭的直接跳过
    MemberOrder update = new MemberOrder();
    update.setStatus(3); update.setCloseTime(LocalDateTime.now());
    int rows = orderMapper.update(update, ...eq(id).eq(status, 0));  // WHERE status=0 只关一次
    if (rows > 0) { order.setStatus(3); cacheOrder(order); }
}
```

**6.5 查询：缓存优先**

```java
private MemberOrder getByIdFromCacheOrDb(String orderId) {
    String key = RabbitConstants.CACHE_ORDER_PREFIX + orderId;
    String json = stringRedisTemplate.opsForValue().get(key);
    if (json != null) return objectMapper.readValue(json, MemberOrder.class); // 缓存命中
    MemberOrder order = orderMapper.selectOne(...);   // 缓存没中，查库
    if (order != null) cacheOrder(order);             // 回填缓存
    return order;
}
```

> **缓存类比**：图书馆借书，管理员先看"门口的白板"（Redis）有没有记录，有就直接抄，没有才去书库翻（MySQL）并把结果记到白板上。白板比书库快得多，MySQL 的负担就小了。**注意**：写操作（下单/支付）必须直接写库，只有读操作才能走缓存。

### 第 7 步：消费者（MQ 监听器）

`OrderListener` 用 `@RabbitListener` 监听两个队列，展示两种可靠性场景。

**7.1 会员升级消费者：手动 ACK + 异常重回队列**

```java
@RabbitListener(queues = RabbitConstants.Q_MEMBER_UPGRADE)
public void handleUpgrade(UpgradeMessage msg,
                          @Header(AmqpHeaders.DELIVERY_TAG) long deliveryTag,
                          Channel channel) throws Exception {
    try {
        // 演示开关：simulateError=true 且第 1 次消费时故意抛异常 -> 重回队列
        boolean firstAttempt = Boolean.FALSE.equals(stringRedisTemplate.hasKey(RETRY_PREFIX + orderId));
        if (Boolean.TRUE.equals(msg.getSimulateError()) && firstAttempt) {
            throw new RuntimeException("模拟消费者处理异常（第 1 次），消息将重回队列重试");
        }
        orderService.upgradeMember(msg);            // 真正业务（内部有幂等）
        channel.basicAck(deliveryTag, false);       // 成功 -> 手动 ACK 确认
        stringRedisTemplate.delete(RETRY_PREFIX + orderId);
    } catch (Exception e) {
        Long retry = stringRedisTemplate.opsForValue().increment(RETRY_PREFIX + orderId); // 数重试次数
        if (retry <= MAX_RETRY) {                   // 没超上限 -> 重回队列，等会再投一次
            channel.basicNack(deliveryTag, false, true);
        } else {                                    // 超上限 -> 确认丢弃，防止死循环
            channel.basicAck(deliveryTag, false);
            stringRedisTemplate.delete(RETRY_PREFIX + orderId);
        }
    }
}
```

> **手动 ACK 类比**：商家发货，你**验收合格才签字**（basicAck）。不合格就拒收退回（basicNack + requeue），商家重发。如果你默认自动签收，一旦处理中程序崩了，消息就"假装成功"丢掉了。

**7.2 延时关单消费者**

```java
@RabbitListener(queues = RabbitConstants.Q_ORDER_CLOSE)
public void handleClose(String orderId, ... long deliveryTag, Channel channel) {
    try {
        orderService.closeExpiredOrder(orderId);    // 关掉未支付订单
        channel.basicAck(deliveryTag, false);       // 成功确认
    } catch (Exception e) {
        channel.basicNack(deliveryTag, false, true); // 失败重回队列，保证不丢
    }
}
```

### 第 4 步：页面组装（Recharge.vue）

页面按"从上到下"分四块：**会员横幅 → 等级卡片 → 操作区（下单/支付） → 订单表格**。

核心逻辑（配合上一课学的 Vue3 组合式 API）：

```js
// 当前待支付订单：从订单列表推导（不是独立 ref！）
// 为什么用 computed？页面刷新后 loadAll() 会重新加载订单列表，
// 待支付订单自动"复活"，始终能继续"模拟支付"——这就是上一课踩坑后学到的教训
const currentOrder = computed(() => orders.value.find((o) => o.status === 0) || null)

async function loadAll() {
  // 三个接口并行请求（Promise.all），一次刷新全部数据
  const [lv, info, list] = await Promise.all([getMemberLevels(), getMemberInfo(), getMyOrders()])
  levels.value = lv.data
  if (lv.data.length) selectedLevel.value = lv.data[0].level
  memberInfo.value = info.data
  orders.value = list.data
}

async function handleCreate() {
  // 防重复：提交中再次点击，前端先拦住并提示（后端分布式锁是第二道保险）
  if (submitting.value) { showMsg('正在处理中，请勿重复提交'); return }
  submitting.value = true
  message.value = ''
  try {
    const res = await createOrder({ level: selectedLevel.value })
    await loadAll()
    showMsg('下单成功：' + res.data.orderId, 'success')
  } catch (e) {
    showMsg(e.message || '下单失败')   // 展示后端业务提示（e.message 来自 axios 拦截器）
  } finally {
    submitting.value = false
  }
}

async function handlePay() {
  if (!currentOrder.value || paying.value) return
  paying.value = true
  try {
    await payOrder(currentOrder.value.orderId, simulateError.value)
    await loadAll()
    showMsg('支付成功，会员升级消息已发送...', 'success')
  } catch (e) {
    showMsg(e.message || '支付失败')
  } finally {
    paying.value = false
  }
}
```

**模板里的关键点**：订单状态 `status` 直接控制显示（`0=待支付` 显示"模拟支付"按钮），状态徽标按颜色区分。

## 5. 踩坑记录（今天实际遇到的真问题）

### 坑 1：RabbitMQ 连接被重置（einval 崩溃）—— 版本不兼容
- **现象**：客户端一握手、一打开 channel，连接就被重置；日志里服务端节点持续 `einval` 崩溃，累计 1500+ 次。
- **根因**：环境是 **RabbitMQ 3.11.5 + Erlang 26.2.5.6**。3.11.x 只支持 Erlang 25.x，这个不兼容组合导致服务端在处理 channel 时 socket 返回 `einval` 崩溃。
- **解决**：升级到 **RabbitMQ 3.13.7**（官方支持 Erlang 26.2）。装好后用裸 TCP 发包验证：握手 → open → **channel.open** → declare 全部通过。
- **教训**：**版本匹配是第一位的**。中间件版本和它的运行环境（Erlang/JDK）必须查官方兼容矩阵。

### 坑 2：快速连点"下单"没有任何提示
- **现象**：连点下单，看不到"正在处理中，请勿重复提交"。
- **根因**：前端 `:disabled="submitting"` 把按钮直接禁用了，第二次点击根本不触发事件——请求都没发，自然没提示。
- **解决**：按钮不再因 `submitting` 禁用，改为在 `handleCreate` 里拦截：提交中再次点击 → 提示"正在处理中，请勿重复提交"。后端分布式锁仍是真正的第二道防线。
- **教训**：**禁用按钮会吞掉点击事件**。既要防重复，又要给反馈，就要在函数入口判断而不是禁用按钮。

### 坑 3：页面刷新后订单"消失"，无法支付也无法再下单
- **现象**：下单（未支付）后浏览器 F5 刷新，带"模拟支付"按钮的订单卡片消失；订单列表仍显示待支付，但又不能再下单（后端拦截"有待支付订单"）——**死锁**。
- **根因**：`currentOrder` 是组件内 `ref`，刷新后重置为 `null`。
- **解决**：把 `currentOrder` 改成 `computed`，**从订单列表推导**待支付订单。刷新后 `loadAll()` 一加载订单，待支付订单自动"复活"。
- **教训**：**页面状态分两类**——刷新后无所谓（临时态）和刷新后必须恢复（业务态）。待支付订单是业务态，必须能从服务端重新推导，不能只存在组件内存里。

### 坑 4：AMQP 测试脚本编码 bug（自制"假崩溃"）
- **现象**：`connection.open` 报错"连接被重置"，误以为服务端有问题。
- **根因**：测试脚本把 `capabilities` 嵌套表编码坏了（少了一层递归），服务端解析失败而断开；另一处把 `channel_max=0` 当成"无限制"，超出 3.13 的 2047 上限被拒。
- **教训**：排查问题时，**先把客户端脚本调对**，再怀疑服务端。看服务端日志里的具体报错（`function_clause` / `negotiation`）比猜测高效得多。

## 7. 进阶方向（练完这些再往深处走）

1. **事务一致性**：下单 + 发消息做不到真正原子。进阶：用**本地消息表**或 **Spring 事务消息**（`@TransactionalEventListener`）保证"库和 MQ 都成功或都失败"。
2. **可靠投递落地**：当前 confirm 失败只打日志。进阶：失败消息落**重试表** + 定时任务补偿重发。
3. **死信更完整**：当前超上限消息被丢弃。进阶：加**人工处理队列**（`order.dead.queue`），消费者把异常消息转到人工处理，方便复查。
4. **分布式锁升级**：`setIfAbsent` 简单锁没有"可重入"和"看门狗续期"。进阶：用 **Redisson** 的 `RLock`。
5. **缓存一致性**：当前"先更新库再更新缓存"，极端情况下可能不一致。进阶：学习 **Cache-Aside / 双删 / Canal 订阅 binlog**。
6. **延时任务进阶**：TTL 死信队列适合"单条延时不同"；但大量消息有**队列级 TTL 头阻塞**问题。进阶：用 **RabbitMQ 延时插件** 或 **Redis ZSet** 实现延时队列。
7. **幂等更严谨**：当前幂等标记 1 天过期。进阶：订单表加**唯一索引 + 重复插入捕获**作为兜底幂等。

## 8. 一句话总结

**编写顺序的核心原则是"按依赖倒序"**：数据库 → 常量 → 实体/Mapper → DTO/VO → MQ 配置 → 业务 → 消费者 → 控制器 → 前端。每一层只依赖它下面的层，从下往上写，每写完一层都能编译、能验证，心里有底。

**技术落点**：Redis 管"防重/缓存/幂等"三种场景；RabbitMQ 管"可靠投递 + 延时任务 + 重试"三种场景。两句话概括全篇：

> **下单** = 拿锁防重 → 写库 → 写缓存 → 发延时消息；
> **支付** = 置已支付 → 发升级消息 → 消费者幂等 + 手动 ACK → 升级会员。
