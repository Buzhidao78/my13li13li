# 08 会员订单（会员充值 + RabbitMQ 可靠投递）

## 模块简介

会员订单模块实现"会员充值"完整闭环：用户选择会员等级（白银/黄金/钻石）下单 → 模拟支付 → 支付成功后异步升级会员 → 未支付订单到期自动关闭。它是本项目的核心练习模块，聚合了两大中间件：**Redis**（分布式锁防重复下单、订单缓存、MQ 消费幂等、发送失败补偿队列）与 **RabbitMQ**（生产端 confirm/return 可靠投递、TTL + 死信队列实现延时关单、手动 ACK + 重试）。

业务链路为异步驱动：支付成功后不直接改会员，而是发一条"会员升级"MQ 消息，由消费者 `OrderListener` 完成升级；下单后发一条带 TTL 的延时消息，到期自动转投死信队列，由消费者关闭未支付订单。为演示可靠投递，本项目还实现了**失败补偿**：任何环节消息发送失败（confirm 失败/路由失败/抛异常），都会把 `{类型}|{orderId}` 写入 Redis 失败队列，由定时任务 `MqCompensateTask` 每 30 秒重发兜底。

### 1. 会员等级常量 `constant/MemberLevel.java`

public class MemberLevel {

### 4. 下单流程 `OrderServiceImpl.createOrder()`（Redis 分布式锁 + 缓存 + TTL 消息）

```java
@Override
public MemberOrderVO createOrder(Long userId, Integer level) {
    // 1. 校验等级是否可购买（只能是 白银/黄金/钻石）
    if (level == null || !MemberLevel.isValid(level)) {
        throw new BusinessException("会员等级不合法");
    }

    // 2. Redis 分布式锁：防止同一个用户重复点击下单
    //    setIfAbsent 是原子操作：key 不存在才设置成功，返回 true 表示拿到锁
    //    锁带 5 秒过期，防止程序崩溃后锁永远不释放（死锁）
    String lockKey = RabbitConstants.LOCK_ORDER_PREFIX + userId;
    Boolean locked = stringRedisTemplate.opsForValue()
            .setIfAbsent(lockKey, "1", Duration.ofSeconds(5));
    if (locked == null || !locked) {
        throw new BusinessException("正在处理中，请勿重复提交");
    }

    try {
        // 3. 双保险：查数据库是否已有待支付订单（防止锁过期后用户又点了一次）
        Long pendingCount = orderMapper.selectCount(new LambdaQueryWrapper<MemberOrder>()
                .eq(MemberOrder::getUserId, userId)
                .eq(MemberOrder::getStatus, 0));
        if (pendingCount != null && pendingCount > 0) {
            throw new BusinessException("您有待支付的订单，请先完成支付");
        }

        // 4. 组装订单并入库（状态 0=待支付）
        MemberLevel.Info info = MemberLevel.of(level);
        MemberOrder order = new MemberOrder();
        order.setOrderId(generateOrderId());
        order.setUserId(userId);
        order.setLevel(level);
        order.setAmount(info.amount);
        order.setDays(info.days);
        order.setStatus(0);
        orderMapper.insert(order);

        // 5. 订单信息写 Redis 缓存（读多写少，缓存能明显减轻 MySQL 压力）
        cacheOrder(order);

        // 6. 发送 TTL 延时消息：消息在 TTL 队列"躺" ttlMs 毫秒，
        //    到期后自动转投死信交换机 -> 关单队列 -> 消费者关闭未支付订单
        sendOrderCloseMessage(order.getOrderId());
        return MemberOrderVO.from(order);
    } finally {
        // 7. 释放分布式锁（无论成功失败都要释放）
        stringRedisTemplate.delete(lockKey);
    }
}
```

**防重复三道防线**：前端 `submitting` 按钮拦截 → Redis 分布式锁（`setIfAbsent` 原子性）→ 数据库查待支付订单兜底（锁过期场景）。

订单号生成规则为"时间戳 + 4 位随机数"，如 `202608211530001234`；TTL 时长来自配置 `order.ttl-ms: 30000`（默认 30 秒，练习方便观察延时关单）。

### 5. 模拟支付 `OrderServiceImpl.payOrder()`（防重复支付 CAS + 发升级消息）

```java
@Override
public MemberOrderVO payOrder(Long userId, String orderId, boolean simulateError) {
    // 1. 直接查数据库（写操作以库为准，不走缓存）
    MemberOrder order = orderMapper.selectOne(new LambdaQueryWrapper<MemberOrder>()
            .eq(MemberOrder::getOrderId, orderId));
    if (order == null) {
        throw new BusinessException("订单不存在");
    }
    if (!order.getUserId().equals(userId)) {
        throw new BusinessException("无权操作该订单");
    }
    if (order.getStatus() != 0) {
        throw new BusinessException("订单状态不允许支付，请刷新后查看");
    }

    // 2. 更新订单为已支付：WHERE status=0 保证并发下只有一次成功（防重复支付）
    MemberOrder update = new MemberOrder();
    update.setStatus(1);
    update.setPayTime(LocalDateTime.now());
    int rows = orderMapper.update(update, new LambdaQueryWrapper<MemberOrder>()
            .eq(MemberOrder::getId, order.getId())
            .eq(MemberOrder::getStatus, 0));
    if (rows == 0) {
        throw new BusinessException("订单状态已变化，支付失败");
    }
    // 3. 刷新缓存中的订单状态
    order.setStatus(1);
    order.setPayTime(update.getPayTime());
    cacheOrder(order);

    // 4. 发送"会员升级"MQ 消息（异步：支付成功 -> 通知消费者升级会员）
    UpgradeMessage msg = new UpgradeMessage();
    msg.setOrderId(orderId);
    msg.setUserId(userId);
    msg.setLevel(order.getLevel());
    msg.setDays(order.getDays());
    msg.setSimulateError(simulateError);
    sendMemberUpgradeMessage(msg);
    return MemberOrderVO.from(order);
}
```

**防重复支付**用"CAS 式更新"：`UPDATE ... WHERE id=? AND status=0`，并发下只有一个请求能改到行（`rows==1`），其余请求得到 `rows==0` 报错。

### 6. 可靠发送封装（失败自动进 Redis 补偿队列）

`sendOrderCloseMessage` 为消息单独设置过期时间（per-message TTL），`sendMemberUpgradeMessage` 直接发对象（由 `Jackson2JsonMessageConverter` 转 JSON）。两者的 `CorrelationData` id 都带类型前缀（`CLOSE:`/`UPGRADE:`），confirm 失败时能据此自动补偿。发送抛异常时写失败队列、不阻塞主流程：

```java
private void sendOrderCloseMessage(String orderId) {
    try {
        rabbitTemplate.convertAndSend(
                RabbitConstants.EX_ORDER_TTL,
                RabbitConstants.RK_ORDER_CREATE,
                orderId,
                // 给这条消息单独设置过期时间（毫秒）
                message -> {
                    message.getMessageProperties().setExpiration(String.valueOf(ttlMs));
                    return message;
                },
                // CorrelationData id 带类型前缀，confirm 失败时据此自动补偿
                new CorrelationData(RabbitConstants.FAIL_TYPE_CLOSE + ":" + orderId));
    } catch (Exception e) {
        log.error("延时关单消息发送异常，已记入补偿队列, orderId={}", orderId, e.getMessage());
        recordFail(RabbitConstants.FAIL_TYPE_CLOSE, orderId);
    }
}

/** 写入失败补偿队列：元素格式 {类型}|{orderId}，MqCompensateTask 每 30 秒取出重发 */
private void recordFail(String type, String orderId) {
    try {
        stringRedisTemplate.opsForList().leftPush(RabbitConstants.FAIL_LIST_KEY, type + "|" + orderId);
    } catch (Exception e) {
        log.error("MQ 失败补偿写入 Redis 异常, {}|{}, 原因={}", type, orderId, e.getMessage());
    }
}
```

### 7. MQ 配置 `config/RabbitMQConfig.java`（可靠投递 + 死信）

改造 `RabbitTemplate` 接入 **confirm 回调**（消息是否到达交换机，第 1 道保险）与 **return 回调**（消息是否路由到队列，第 2 道保险，`mandatory=true` 触发）。confirm 失败按消息 id 前缀识别类型入补偿队列；return 失败没有 correlation id，只能从消息体反推（关单消息体是 JSON 字符串订单号、升级消息体是 `{"orderId":...}` JSON）：

```java
@Bean
public RabbitTemplate rabbitTemplate(ConnectionFactory connectionFactory, MessageConverter messageConverter) {
    RabbitTemplate template = new RabbitTemplate(connectionFactory);
    template.setMessageConverter(messageConverter);
    template.setMandatory(true); // mandatory=true：消息路由不到任何队列时，触发 return 回调

    // confirm 回调：每条消息投递后都会回调，ack=true 表示交换机已收到
    template.setConfirmCallback((correlationData, ack, cause) -> {
        String id = correlationData != null ? correlationData.getId() : null;
        if (ack) {
            log.info("MQ confirm 成功：消息已投递到交换机, id={}", id);
        } else {
            // 确认失败（如交换机不存在 / 连接异常）：记入失败补偿队列，等待定时任务重发
            log.error("MQ confirm 失败：消息未投递到交换机, id={}, 原因={}，已记入补偿队列", id, cause);
            if (id != null) {
                enqueueByMessageId(id);
            }
        }
    });
    // return 回调：路由失败（交换机没找到匹配的队列）时回调，可在此做补偿/记录
    template.setReturnsCallback(returned -> {
        log.error("MQ return 路由失败：exchange={}, routingKey={}，已记入补偿队列",
                returned.getExchange(), returned.getRoutingKey());
        enqueueByMessageBody(new String(returned.getMessage().getBody()));
    });
    return template;
}
```

**延时关单**通过"TTL 队列 + 死信交换机"实现：`orderTtlQueue` 声明 `x-dead-letter-exchange` 和 `x-dead-letter-routing-key`，消息在 TTL 队列躺到期后自动转投死信交换机 → 关单队列：

```java
@Bean
public Queue orderTtlQueue() {
    Map<String, Object> args = new HashMap<>();
    args.put("x-dead-letter-exchange", RabbitConstants.EX_ORDER_DLX);
    args.put("x-dead-letter-routing-key", RabbitConstants.RK_ORDER_CLOSE);
    return new Queue(RabbitConstants.Q_ORDER_TTL, true, false, false, args);
}
```

### 8. 消费者 `listener/OrderListener.java`（手动 ACK + 幂等 + 重试）

`handleUpgrade` 监听升级队列，演示三个可靠性机制：**手动 ACK**（成功才 `basicAck`）、**Redis 幂等**（重复投递直接跳过，见 `upgradeMember`）、**异常重回队列**（`simulateError=true` 且首次消费时故意抛异常；重试次数存 Redis `retry:{orderId}`，超过上限 3 次后丢弃防止死循环）：

```java
@RabbitListener(queues = RabbitConstants.Q_MEMBER_UPGRADE)
public void handleUpgrade(UpgradeMessage msg,
                          @Header(AmqpHeaders.DELIVERY_TAG) long deliveryTag,
                          Channel channel) throws Exception {
    String orderId = msg.getOrderId();
    try {
        // 演示开关：simulateError=true 且是第 1 次消费时，故意抛异常 -> 消息重回队列重试
        boolean firstAttempt = Boolean.FALSE.equals(stringRedisTemplate.hasKey(RabbitConstants.RETRY_PREFIX + orderId));
        if (Boolean.TRUE.equals(msg.getSimulateError()) && firstAttempt) {
            throw new RuntimeException("模拟消费者处理异常（第 1 次），消息将重回队列重试");
        }
        // 真正的业务处理（内部有 Redis 幂等判断，重复消息直接跳过）
        orderService.upgradeMember(msg);
        // 处理成功 -> 手动 ACK（告诉 RabbitMQ 这条消息处理完了，可以从队列删除）
        channel.basicAck(deliveryTag, false);
        stringRedisTemplate.delete(RabbitConstants.RETRY_PREFIX + orderId);
    } catch (Exception e) {
        // 处理失败：统计重试次数
        Long retry = stringRedisTemplate.opsForValue().increment(RabbitConstants.RETRY_PREFIX + orderId);
        if (retry <= MAX_RETRY) {
            // 未超过上限 -> 重回队列（requeue=true），RabbitMQ 会再次投递给消费者
            channel.basicNack(deliveryTag, false, true);
        } else {
            // 超过上限 -> 确认丢弃（防止消息死循环）；生产环境一般会转入人工处理/专门的死信
            channel.basicAck(deliveryTag, false);
        }
    }
}
```

`handleClose` 监听关单队列：收到死信转投来的订单号后调用 `closeExpiredOrder`，失败 `basicNack` 重回队列。

### 9. 会员升级 `OrderServiceImpl.upgradeMember()`（消费幂等）

```java
@Override
public void upgradeMember(UpgradeMessage msg) {
    String orderId = msg.getOrderId();

    // 1. MQ 消费幂等：Redis 里已存在"已处理"标记，说明这条消息处理过了，直接跳过
    String idempotentKey = RabbitConstants.IDEMPOTENT_PREFIX + orderId;
    if (Boolean.TRUE.equals(stringRedisTemplate.hasKey(idempotentKey))) {
        log.info("幂等命中：订单 {} 已处理过，跳过本次消费", orderId);
        return;
    }
    // 2. 校验订单确实已支付（防止消息被伪造或提前到达）
    MemberOrder order = orderMapper.selectOne(...);
    if (order == null || order.getStatus() != 1) {
        throw new BusinessException("订单未支付，不能升级会员");
    }
    // 3. 升级会员：等级取更高者（买黄金不会把钻石降级），时长在原来基础上叠加
    User user = userMapper.selectById(msg.getUserId());
    LocalDateTime now = LocalDateTime.now();
    // 原到期时间若还没过期，则从原到期时间继续累加；已过期则从现在开始
    LocalDateTime base = user.getMemberExpire();
    LocalDateTime newExpire = (base != null && base.isAfter(now)) ? base : now;
    newExpire = newExpire.plusDays(msg.getDays());
    int newLevel = Math.max(user.getMemberLevel() == null ? 0 : user.getMemberLevel(), msg.getLevel());

    User updateUser = new User();
    updateUser.setId(user.getId());
    updateUser.setMemberLevel(newLevel);
    updateUser.setMemberExpire(newExpire);
    userMapper.updateById(updateUser);
    // 4. 处理成功后写入幂等标记（TTL 1 天，足够覆盖消息重试窗口）
    stringRedisTemplate.opsForValue().set(idempotentKey, "1", Duration.ofDays(1));
}
```

**升级规则**：等级取更高者（买黄金不会把钻石降级）；时长从"原到期时间"（未过期）或"当前时间"（已过期）起叠加，即续费累加。

### 10. 延时关单 `OrderServiceImpl.closeExpiredOrder()` 与补偿任务 `MqCompensateTask`

关单只处理"待支付"订单：状态 `0 → 3`（已过期），`WHERE status=0` 保证只关闭一次，然后同步刷新缓存：

```java
@Override
public void closeExpiredOrder(String orderId) {
    MemberOrder order = orderMapper.selectOne(...);   // 查订单，不存在直接返回（消息幂等）
    if (order == null) { ... return; }
    if (order.getStatus() != 0) { ... return; }        // 只有待支付才需关闭

    MemberOrder update = new MemberOrder();
    update.setStatus(3);
    update.setCloseTime(LocalDateTime.now());
    int rows = orderMapper.update(update, new LambdaQueryWrapper<MemberOrder>()
            .eq(MemberOrder::getId, order.getId())
            .eq(MemberOrder::getStatus, 0));           // WHERE status=0 保证只关闭一次
    if (rows > 0) {
        order.setStatus(3);
        order.setCloseTime(update.getCloseTime());
        cacheOrder(order);
    }
}
```

`MqCompensateTask` 每 30 秒从 Redis 失败队列 `rightPop` 取出条目（入队用 `leftPush`，先进先被取走），按 `CLOSE|orderId` / `UPGRADE|orderId` 分派给 `resendCloseMessage` / `resendUpgradeMessage`。**补偿内部有幂等校验**：关单消息只有订单仍存在且仍待支付才重发；升级消息只有"已支付且无幂等标记"才重发。处理抛异常的条目放回队尾稍后重试，避免毒丸消息打断整个任务：

```java
@Scheduled(fixedDelay = 30_000)
public void compensate() {
    for (int i = 0; i < MAX_PER_RUN; i++) {   // MAX_PER_RUN=100，防止任务长时间占用
        String item = stringRedisTemplate.opsForList().rightPop(RabbitConstants.FAIL_LIST_KEY);
        if (item == null) break;
        // 解析 {类型}|{orderId}
        String type = item.substring(0, idx);
        String orderId = item.substring(idx + 1);
        try {
            if (RabbitConstants.FAIL_TYPE_CLOSE.equals(type)) {
                orderService.resendCloseMessage(orderId);
            } else if (RabbitConstants.FAIL_TYPE_UPGRADE.equals(type)) {
                orderService.resendUpgradeMessage(orderId);
            }
        } catch (Exception e) {
            // 重发/查询抛异常：放回队尾，等下一轮再试（避免毒丸消息打断整个任务）
            stringRedisTemplate.opsForList().leftPush(RabbitConstants.FAIL_LIST_KEY, item);
        }
    }
}
```

### 11. 查询与会员信息

- `getOrder`：优先读 Redis 缓存（`order:{orderId}`），反序列化失败回源数据库并回填缓存，缓存 TTL = `ttlMs + 10s`（保证关单消息处理时缓存还在）；
- `listMyOrders`：`selectPage` + `orderByDesc(createTime)`，转 `MemberOrderVO` 返回（records/total 供前端分页）；
- `getPendingOrder`：查最新一条 `status=0` 的订单（`LIMIT 1`），无论订单列表翻到第几页，页面顶部"继续支付"入口都有效；
- `getMemberInfo`：等级 + 到期时间 + `isMember`（到期时间晚于当前才算）+ `remainDays`（`ChronoUnit.DAYS.between` 取整天数）。

## 关键设计说明

### 1. "MQ 可靠投递 + 补偿"完整链路

一条"下单 → 延时关单"消息要经历：① 发送时带 `CorrelationData("CLOSE:orderId")`；② RabbitTemplate 的 confirm 回调确认是否到达交换机、return 回调确认是否路由到队列；③ 任何一步失败（或 `convertAndSend` 抛异常）→ 写 Redis 失败队列 `mq:fail:list`；④ `MqCompensateTask` 每 30 秒扫描重发；⑤ 重发前二次校验订单状态（幂等），避免重复补偿产生副作用。**即使 MQ 全程不可用，消息也不会丢**——失败条目躺在 Redis 里等 MQ 恢复后补发，这就是"最终一致"的兜底。

### 2. 延时关单为什么用"TTL + 死信队列"而不是定时任务

定时轮询数据库（如每 5 分钟扫一次待支付订单）实现简单但精度差、有扫描压力；TTL + DLX 方案由 RabbitMQ 精准控制每个订单的关闭时机（per-message TTL），且**关单动作本身就是一次 MQ 消费**，天然享受手动 ACK/重试的可靠性。代价是需要多声明一套交换机/队列，配置集中在 `RabbitMQConfig` 中。

### 3. 幂等贯穿全链路

- **下单幂等**：Redis 分布式锁 + 待支付订单查重；
- **支付幂等**：`WHERE status=0` 的 CAS 更新；
- **消费幂等**：升级前查 `processed:{orderId}`，处理后写 TTL 1 天的幂等标记（覆盖消息重试窗口）；
- **补偿幂等**：`resendCloseMessage` / `resendUpgradeMessage` 内部都先校验订单状态。

每层幂等都独立成立，即使上层失守（如锁过期），下层也能兜住。

### 4. 缓存与数据库的一致性策略

订单是"读多写少"数据，查询走 Redis 缓存（TTL = `ttlMs + 10s`，略长于关单延时，保证关单处理时缓存仍可命中）。每次状态变更（支付/关单）都在写库成功后**同步刷新缓存**，缓存失败仅记日志、降级为只查库，不阻塞主流程。

## 常见问题

### 1. 连续快速点两次"下单"，为什么只会成功一次？

三层防线：前端 `submitting` 先拦截；并发请求到达后端时，Redis `setIfAbsent` 只有第一个能拿到锁（返回"正在处理中，请勿重复提交"）；即使锁 5 秒过期后又来一次，数据库查询"已有待支付订单"也会拦下。三层逐级兜底，避免重复下单。

### 2. 支付成功后会员等级为什么没有立刻变化？

升级是异步的：支付接口只改订单状态并发 MQ 消息，由 `OrderListener.handleUpgrade` 消费后调用 `upgradeMember` 改用户会员字段。正常情况下毫秒级完成；如果消费者报错，消息会重回队列重试（最多 3 次），重试期间会员等级暂不变，最终会成功（或超限丢弃并记日志）。

### 3. 勾选"演示模拟报错"支付后，消息去哪了？

支付时 `simulateError=true`，消费者第 1 次消费故意抛异常 → `basicNack(requeue=true)` 消息重回队列 → 第 2 次消费正常处理并 ACK。页面日志可以看到"消费者处理失败（第1次），消息重回队列"再到"已成功消费并确认"，这正是 MQ 自带重试机制的直观演示。

### 4. 30 秒的 TTL 会不会太短，生产环境怎么调？

`order.ttl-ms: 30000` 是写在 `application.yml` 的配置项，练习设为 30 秒是为了方便观察"下单 → 刷新 → 状态变已过期"的完整链路。生产环境一般设为 15~30 分钟，改配置即可，代码无需变动。
