# 视频上传与管理模块

## 模块简介

视频上传与管理模块是社区的「内容供给」核心：UP 主上传视频 → 文件落盘 → 入库进入审核状态机 → 管理员审核 → 发布/驳回 → 前台展示，并提供下架、重新上架、删除（级联清理）等管理能力。同时承担视频流的构建（最新/最热/分类/关注动态）与**播放量高并发计数**（Redis INCR 增量 + 定时任务落库 MySQL）。

上传链路有两个值得注意的工程点：一是**无封面自动用 FFmpeg 抽取视频首帧**兜底，且抽帧失败绝不让投稿流程中断（封面是可选字段）；二是**播放量不直接写 MySQL**——每次播放只做一次 Redis `INCR`（毫秒级、扛得住高并发），由 `CountSyncTask` 每 5 分钟把增量批量刷进数据库，极端情况最多丢 5 分钟增量，业务上可接受。

## 功能清单

| 功能 | 说明 | 涉及接口/组件 |
| ---- | ---- | ---- |
| 视频上传 | multipart 接收文件/封面，校验+落盘+入库（默认待审核） | `POST /api/video/upload`，`VideoServiceImpl.upload()` |

| 审核状态机 | 待审核 → 已发布 / 已驳回；仅管理员可审 | `POST /api/video/{id}/audit`，`audit()` |
| 下架/重新上架 | 已发布 → 已下架 → 已发布（作者或管理员） | `POST .../offline`、`POST .../republish` |
| 删除视频 | 硬删除 + 级联清理评论/收藏/历史/投币/通知 + Redis key + 磁盘文件 | `DELETE /api/video/{id}`，`deleteVideo()` |
| 播放计数 | Redis INCR 增量 + 观看历史；定时任务落库 | `POST /api/video/{id}/play`，`CountSyncTask` |

| 详情页 | 合并 Redis 增量准实时计数、点赞态、评论数、权限控制 | `GET /api/video/detail/{id}`，`detail()` |

## 涉及数据表

**`video` 表**（见 `backend/src/main/resources/db/init.sql`）：

| 字段 | 类型 | 作用 |
| ---- | ---- | ---- |
| id | BIGINT 自增 | 主键 |
| user_id | BIGINT | 上传用户 ID（`idx_user_id` 索引） |
| title / description | VARCHAR | 标题（≤100 字）、简介（≤500 字） |
| video_url | VARCHAR(255) | 视频访问路径（如 `/upload/20260907/xxx.mp4`） |
| cover_url | VARCHAR(255) | 封面访问路径（可选，无封面时 FFmpeg 抽帧兜底） |
| category | TINYINT | 分类：0默认 1生活 2游戏 3科技 4美食 |
| status | TINYINT | 0待审核 1已发布 2已驳回 3已下架（`constant/VideoStatus`） |
| play_count / like_count / favorite_count / coin_count | INT | 播放量/点赞/收藏/投币计数 |
| create_time / update_time | DATETIME | 创建/更新时间 |

建表要点：`idx_status_time (status, create_time)` 支撑首页「已发布 + 时间倒序」查询；`idx_category_time (category, create_time)` 支撑分类页；排序条件直接命中复合索引，避免 filesort。

## 后端实现

### 1. 上传接口与存储目录

`VideoController.upload()` 用 `@RequestParam` 接收 multipart 字段；`VideoServiceImpl.upload()` 标了 `@Transactional`，**入库失败时回滚并清理刚写入磁盘的文件**，避免留下「无记录的孤儿文件」：

```java
@Override
@Transactional(rollbackFor = Exception.class)
public VideoVO upload(Long userId, MultipartFile file, MultipartFile cover,
                      String title, String description, Integer category) {
    if (!StringUtils.hasText(title)) {
        throw new BusinessException("视频标题不能为空");
    }
    if (title.length() > 100) {
        throw new BusinessException("视频标题不能超过 100 字");
    }

    String videoUrl = uploadUtils.saveVideo(file);
    // 封面：优先用用户上传的封面；未上传时用 FFmpeg 抽取视频首帧兜底（抽取失败则封面为 null，不阻塞投稿）
    String coverUrl = (cover == null || cover.isEmpty())
            ? uploadUtils.extractCoverFromVideo(videoUrl)
            : uploadUtils.saveImage(cover);

    Video video = new Video();
    video.setUserId(userId);
    video.setTitle(title.trim());
    video.setVideoUrl(videoUrl);
    video.setCoverUrl(coverUrl);
    video.setCategory(category == null ? 0 : category);
    video.setStatus(VideoStatus.PENDING);   // 默认"待审核"，前台不可见
    video.setPlayCount(0);
    video.setLikeCount(0);
    video.setFavoriteCount(0);
    video.setCoinCount(0);
    try {
        videoMapper.insert(video);
    } catch (RuntimeException e) {
        // 入库失败：清理刚写入磁盘的文件，避免留下"无记录的孤儿文件"
        uploadUtils.deleteIfExists(videoUrl);
        uploadUtils.deleteIfExists(coverUrl);
        throw e;
    }
    return VideoVO.from(video, null);
}
```

**存储目录设计**（`util/UploadUtils.java`）：`save()` 统一做「扩展名白名单 + Content-Type 兜底 + 大小限制（视频 100MB / 图片 5MB）」三层校验，然后按 `{uploadDir}/{yyyyMMdd}/` 日期分目录、UUID 命名，防止重名覆盖，也方便按时间管理：

```java
// 4. 生成存储目录：{uploadDir}/{yyyyMMdd}/，目录不存在就创建
String dateDir = LocalDate.now().format(DateTimeFormatter.ofPattern("yyyyMMdd"));
Path dir = Paths.get(uploadDir, dateDir);
Files.createDirectories(dir);
// 5. 生成唯一文件名：UUID + 扩展名（避免重名覆盖）
String fileName = UUID.randomUUID().toString().replace("-", "") + "." + ext.toLowerCase(Locale.ROOT);
// 6. 写入磁盘：用 Files.copy 读输入流写目标文件（比 transferTo 更可控、跨容器行为一致）
Path target = dir.resolve(fileName);
Files.copy(file.getInputStream(), target, StandardCopyOption.REPLACE_EXISTING);
// 7. 返回对外访问路径（WebConfig 里已把 /upload/** 映射到这个磁盘目录）
return "/upload/" + dateDir + "/" + fileName;
```

磁盘路径与访问路径分离：磁盘存 `./upload/20260912/xxx.mp4`，对外访问 `/upload/20260912/xxx.mp4`。`config/WebConfig.java` 把 `/upload/**` 映射到磁盘目录（`addResourceLocations` 必须以 `/` 结尾）：

```java
@Override
public void addResourceHandlers(ResourceHandlerRegistry registry) {
    // 注意：addResourceLocations 的路径必须以 / 结尾
    registry.addResourceHandler("/upload/**")
            .addResourceLocations("file:" + uploadDir + "/");
}
```

### 2. FFmpeg 抽首帧：30 秒超时 + 失败容错

`UploadUtils.extractCoverFromVideo()` 用 `ProcessBuilder` 拉起 ffmpeg 子进程抽帧：`-ss 0` 取第 0 秒、`-frames:v 1` 只取 1 帧、`-q:v 2` 高质量 JPG，封面与视频同目录同名（`xxx.mp4` → `xxx.jpg`）。**三种失败场景（文件不存在/超时/退出码非 0 或 FFmpeg 未安装）都返回 null 而不是抛异常**——封面是可选字段，绝不让投稿流程因封面失败而整体中断：

```java
// FFmpeg 抽帧命令：-y 覆盖已存在、-i 输入视频、-ss 0 从第 0 秒、-frames:v 1 只取 1 帧、-q:v 2 高质量 JPG
ProcessBuilder pb = new ProcessBuilder(
        "ffmpeg", "-y",
        "-i", videoPath.toString(),
        "-ss", "0",
        "-frames:v", "1",
        "-q:v", "2",
        coverPath.toString());
pb.redirectErrorStream(true);
try {
    Process process = pb.start();
    // 读走输出流防止缓冲区写满导致子进程阻塞；最长等 30 秒
    try (var reader = process.getInputStream()) {
        reader.transferTo(OutputStream.nullOutputStream());
    }
    boolean finished = process.waitFor(30, TimeUnit.SECONDS);
    if (!finished) {
        process.destroyForcibly();      // 超时强制杀掉子进程
        log.warn("抽取封面超时: {}", videoUrl);
        return null;
    }
    if (process.exitValue() != 0 || !Files.exists(coverPath)) {
        log.warn("抽取封面失败，ffmpeg 退出码: {}", process.exitValue());
        return null;
    }
} catch (IOException e) {
    // FFmpeg 未安装或执行失败：封面缺省，不让投稿整体失败
    log.warn("抽取封面异常（FFmpeg 不可用?）: {}", videoUrl, e);
    return null;
}
```

### 3. 审核状态机

`constant/VideoStatus.java` 定义了四个状态：待审核(0) → 已发布(1)/已驳回(2)；已发布 → 已下架(3)。`audit()` 在 **service 层校验管理员身份**（`isAdmin(operatorId)`，防止任意登录用户越权），并且只有「待审核」状态才能审核，目标状态只能是已发布或已驳回：

```java
@Override
public void audit(Long id, int status, Long operatorId) {
    // 审核是平台运营动作，只有管理员（role=1）能操作，防止任意登录用户越权
    if (!isAdmin(operatorId)) {
        throw new BusinessException("无权限：仅管理员可审核视频");
    }
    Video video = videoMapper.selectById(id);
    if (video == null) {
        throw new BusinessException("视频不存在");
    }
    if (!video.getStatus().equals(VideoStatus.PENDING)) {
        throw new BusinessException("只有待审核的视频才能审核");
    }
    if (status != VideoStatus.PUBLISHED && status != VideoStatus.REJECTED) {
        throw new BusinessException("审核状态不合法");
    }
    Video update = new Video();
    update.setId(id);
    update.setStatus(status);
    videoMapper.updateById(update);   // 只更新 status 字段
}
```

`listPending()` 还支持状态筛选（`status=0` 待审核、`status=-1` 已审核合并展示、其它数字精确匹配）和关键词搜索（标题模糊或作者昵称/用户名子查询，单引号转义防 SQL 注入），并按 `createTime` 正序排——**先提交的先审**，避免新视频堆积在最后一页。

### 4. 下架 / 重新上架 / 删除

`offline()`（已发布→已下架）与 `republish()`（已下架→已发布）都用 `requireOwnerOrAdmin()` 校验**作者本人或管理员**，且严格限定前置状态，防止状态错乱。`deleteVideo()` 是硬删除，**级联清理五类数据 + Redis key + 磁盘文件**：

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void deleteVideo(Long id, Long operatorId) {
    Video video = videoMapper.selectById(id);
    if (video == null) {
        throw new BusinessException("视频不存在");
    }
    requireOwnerOrAdmin(video, operatorId);
    // 级联清理互动数据：评论/收藏/观看历史/投币/关联通知（避免留下孤儿记录）
    commentMapper.delete(new LambdaQueryWrapper<VideoComment>().eq(VideoComment::getVideoId, id));
    favoriteMapper.delete(new LambdaQueryWrapper<VideoFavorite>().eq(VideoFavorite::getVideoId, id));
    historyMapper.delete(new LambdaQueryWrapper<WatchHistory>().eq(WatchHistory::getVideoId, id));
    coinMapper.delete(new LambdaQueryWrapper<VideoCoin>().eq(VideoCoin::getVideoId, id));
    notificationMapper.delete(new LambdaQueryWrapper<UserNotification>().eq(UserNotification::getVideoId, id));
    videoMapper.deleteById(id);
    // 清理 Redis 中的计数/点赞集合（否则残留 key 会让 detail 显示过期计数）
    stringRedisTemplate.delete(KEY_PLAY + id);
    stringRedisTemplate.delete(KEY_LIKE + id);
    stringRedisTemplate.delete(KEY_LIKE_COUNT + id);
    // 清理磁盘文件：视频本体 + 封面（失败仅记日志，不影响主流程）
    uploadUtils.deleteIfExists(video.getVideoUrl());
    uploadUtils.deleteIfExists(video.getCoverUrl());
}
```

删除是**不可恢复**操作，前端删除前需二次确认（`video.js` 中 `deleteVideo` 注释同样提醒）。

### 5. 播放量：Redis INCR 增量 + 定时落库

`recordPlay()` 只做两件事：`INCR video:play:{id}` 原子自增（不落库）；登录用户记观看历史（同一视频只留一条，靠 `DuplicateKeyException` 捕获唯一约束冲突后改更新时间）：

```java
@Override
public void recordPlay(Long videoId, Long userId) {
    Video video = videoMapper.selectById(videoId);
    if (video == null || !video.getStatus().equals(VideoStatus.PUBLISHED)) {
        throw new BusinessException("视频不存在或未发布");
    }
    // 1. 播放量：Redis 原子自增（高并发下 INCR 不会丢，定时任务再刷进 MySQL）
    stringRedisTemplate.opsForValue().increment(KEY_PLAY + videoId);

    // 2. 登录用户记录观看历史（同一视频只保留一条，重复看只更新时间）
    if (userId != null) {
        WatchHistory history = new WatchHistory();
        history.setVideoId(videoId);
        history.setUserId(userId);
        history.setWatchTime(LocalDateTime.now());
        try {
            historyMapper.insert(history);
        } catch (DuplicateKeyException e) {
            // 唯一约束冲突 = 之前看过，更新观看时间
            WatchHistory exist = historyMapper.selectOne(new LambdaQueryWrapper<WatchHistory>()
                    .eq(WatchHistory::getVideoId, videoId)
                    .eq(WatchHistory::getUserId, userId));
            if (exist != null) {
                exist.setWatchTime(LocalDateTime.now());
                historyMapper.updateById(exist);
            }
        }
    }
}
```

`task/CountSyncTask.java` 每 5 分钟（`fixedDelay = 300_000`）把 Redis 增量刷进 MySQL。核心技巧是**先 `get` 再 `delete` 再落库**——保证同一份增量只落库一次（即使 SQL 失败，最多丢这一次增量，不会重复累加）；用 SQL 原子自增 `count = count + delta` 避免「先查后改」并发互相覆盖：

```java
/**
 * 每 5 分钟执行一次（fixedDelay：等上一次执行完再计时，
 * 避免任务执行时间超过周期时两个实例并发扫同一批 key，导致增量重复落库）
 */
@Scheduled(fixedDelay = 300_000)
public void syncCounts() {
    syncToDb(KEY_PLAY, "play_count");
    syncToDb(KEY_LIKE_COUNT, "like_count");
}

private void syncToDb(String prefix, String column) {
    Set<String> keys = stringRedisTemplate.keys(prefix + "*");
    if (keys == null || keys.isEmpty()) {
        return;
    }
    for (String key : keys) {
        String deltaStr = stringRedisTemplate.opsForValue().get(key);
        if (deltaStr == null || "0".equals(deltaStr)) {
            // 值为空或 0：没有增量，直接清掉 key 避免下次再扫
            stringRedisTemplate.delete(key);
            continue;
        }
        // 先删除再落库：即使下面更新失败，最多丢这一次增量，不会重复累加
        stringRedisTemplate.delete(key);
        try {
            int delta = Integer.parseInt(deltaStr);
            Long videoId = Long.parseLong(key.substring(prefix.length()));
            // 视频不存在（已被删除）：跳过即可，key 已清理
            if (videoMapper.selectById(videoId) == null) {
                continue;
            }
            // SQL 原子自增：count = count + delta，避免"先查后改"在并发下互相覆盖
            videoMapper.update(null, new LambdaUpdateWrapper<Video>()
                    .eq(Video::getId, videoId)
                    .setSql("`" + column + "` = `" + column + "` + (" + delta + ")"));
        } catch (NumberFormatException e) {
            log.warn("计数同步解析失败，key={}", key);
        }
    }
}
```

### 6. 详情页与视频流

`detail()` 做了权限控制（已发布所有人可见；未发布仅作者本人与管理员可见，方便审核时边看边审），并把 **Redis 未落库增量合并到返回结果**（`playCount = DB + Redis 增量`），实现「准实时」计数，不用等 5 分钟落库：

```java
VideoVO vo = toVO(video);
// 播放量 = 数据库值 + Redis 未落库增量（准实时）
String inc = stringRedisTemplate.opsForValue().get(KEY_PLAY + id);
if (inc != null) {
    vo.setPlayCount(video.getPlayCount() + Integer.parseInt(inc));
}
// 点赞数 = 数据库值 + Redis 未落库增量
String likeInc = stringRedisTemplate.opsForValue().get(KEY_LIKE_COUNT + id);
if (likeInc != null) {
    vo.setLikeCount(video.getLikeCount() + Integer.parseInt(likeInc));
}
// 当前用户是否已点赞（登录才查）
if (currentUserId != null) {
    vo.setLiked(Boolean.TRUE.equals(
            stringRedisTemplate.opsForSet().isMember(KEY_LIKE + id, currentUserId.toString())));
}
// 评论数
vo.setCommentCount(Math.toIntExact(commentMapper.selectCount(
        new LambdaQueryWrapper<VideoComment>().eq(VideoComment::getVideoId, id))));
```

视频流四个入口共用同一个 `toVO()`（同样合并 Redis 增量，保证列表页与详情页播放数实时同步）：`list()`（首页，分类可选）、`search()`（标题 LIKE 模糊）、`feed()`（拉模式：先查我关注的用户 id，再 `IN` 查这些人的已发布视频，没关注任何人时返回空分页避免 `IN ()` 语法错误）、`listByUser()`（他人主页）。排序规则统一：`sort=hot` 按播放量倒序（最热），否则按创建时间倒序（最新）：

```java
// 排序：hot=按播放量（最热），默认按发布时间（最新）
if ("hot".equals(sort)) {
    wrapper.orderByDesc(Video::getPlayCount).orderByDesc(Video::getCreateTime);
} else {
    wrapper.orderByDesc(Video::getCreateTime);
}
```

### 2. API 封装 video.js

`frontend/src/api/video.js` 上传接口要点：手动指定 `multipart/form-data`，并把超时从默认 10s 放宽到 60s（大文件上传慢）：

```js
/** 上传视频：formData 里包含 file(视频)、cover(封面)、title、description、category */
export function uploadVideo(formData) {
  return request.post('/video/upload', formData, {
    headers: { 'Content-Type': 'multipart/form-data' },
    timeout: 60000 // 大文件上传可能超过默认 10s，放宽到 60s

```

详情页 `VideoDetail.vue` 用原生 `<video :src="video.videoUrl">` 直接播放后端返回的路径；进入页面调用 `playVideo(id)` 上报一次播放（本地乐观 +1），列表/详情显示的都是合并后的准实时播放数。

## 关键设计说明

**1. 播放量为什么用 Redis 而不是直接 UPDATE MySQL？**

热门视频可能同时有成千上万次播放，若每次都执行 `UPDATE video SET play_count = play_count + 1`，数据库行锁竞争会让 MySQL 成为瓶颈（写放大 + 热点行）。改用 Redis `INCR`（单线程原子操作、纯内存、毫秒级）后，每次播放只花一次内存操作；`CountSyncTask` 每 5 分钟把增量合并成**一条** UPDATE 刷库，写放大降低几千倍。代价是极端情况（Redis 崩溃、任务失败）最多丢 5 分钟增量——对播放量这种「近似统计」完全可接受。

**2. 为什么落库前必须先删除 Redis key？**

如果先落库再删 key，期间新产生的播放会叠加在旧增量上，可能造成**重复累加**。本实现严格按「get → delete → UPDATE」执行：delete 之后即使 UPDATE 失败，最多丢这一次增量，**但永远不会把同一份增量累加两次**。这是「至少一次」与「至多一次」权衡下对计数场景的正确选择。另外用 `fixedDelay`（上一次执行完再计时）避免任务实例并发扫同一批 key。

**3. FFmpeg 抽帧为什么「失败不阻塞投稿」？**

封面是**可选字段**，而投稿是用户的核心操作。如果抽帧失败（FFmpeg 未安装、视频损坏、超时）就让整个投稿回滚，用户会得到一个与「视频上传成功」预期不符的失败，体验很差。所以 `extractCoverFromVideo()` 对超时（30 秒 `waitFor` + `destroyForcibly`）、退出码非 0、IO 异常全部返回 `null`，由前端在无封面时用占位图兜底。同时命令加了 `-q:v 2` 保证抽出的封面质量。

**4. 为什么列表和详情都要合并 Redis 增量？**

`toVO()` 是列表/详情共用的实体转 VO 方法，它和 `detail()` 一样把 Redis 未落库增量加进播放数。如果不这样做，会出现「首页列表播放 0、点进详情播放 4」的错位——增量还没到 5 分钟的落库周期，列表显示的是旧值。合并后**所有入口看到的播放数都是准实时的**，切换页面不再有数字跳变，这也是「读端合并增量」这个通用模式的体现。

## 常见问题

**Q1：上传成功但入库失败，磁盘会残留文件吗？**

不会。`upload()` 的 `@Transactional` 保证入库异常回滚，`catch (RuntimeException)` 块调用 `deleteIfExists()` 把视频和封面都删掉，避免「无记录的孤儿文件」占用磁盘。上传目录按日期分目录 + UUID 命名，也方便运维按天清理。

**Q2：同一个视频被两个人同时审核会怎样？**

`audit()` 先校验状态必须是 `PENDING` 才更新。两个管理员同时审核：先执行的那个把状态改为 1 或 2，后执行的在 `if (!video.getStatus().equals(VideoStatus.PENDING))` 处抛「只有待审核的视频才能审核」，天然幂等，不会出现重复审核覆盖结果。

**Q3：视频删除后，Redis 里的计数 key 会怎样？**

`deleteVideo()` 显式删除 `video:play:{id}`、`video:like:{id}`、`video:like:count:{id}` 三个 key。即使漏删，`CountSyncTask.syncToDb()` 也会先 `selectById` 判断视频是否还存在——已删除的视频直接跳过并清掉 key，双保险保证不把孤儿计数写进数据库。

**Q4：用 KEYS 扫描 Redis 会不会有性能问题？**

`CountSyncTask` 用 `keys(prefix + "*")` 一次性扫出所有增量 key。练习场景数据量小没问题，但生产环境 `KEYS` 会阻塞 Redis 单线程、数据量大时 O(N) 扫描不可接受，代码注释已说明应改用 `SCAN` 游标遍历。同理，评论/收藏的 N+1 联查（逐条 `selectById` 查作者昵称）也是练习规模下的取舍，数据量上来后应改为 `IN` 批量查询。
