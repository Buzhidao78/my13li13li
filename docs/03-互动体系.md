# 互动体系模块

## 模块简介

互动体系是视频社区的「人气引擎」，包含四类用户行为：**点赞**（Redis Set 去重 + 增量计数）、**收藏**（数据库关系表 + 唯一约束去重）、**投币**（每人每天最多 3 枚）、**评论**（楼中楼结构：`parent_id` + `root_id` 双字段设计）。每次互动都会触发**站内通知**给视频作者或被回复人（自己互动自己不通知），形成「用户行为 → 数据更新 → 通知回流」的完整闭环。

模块设计上体现了「不同数据用不同存储」的取舍：点赞状态是**高频、量级大、价值密度低**的（点一下赞只是一个布尔状态），放 Redis Set 里天然去重、查询 O(1)、还能顺带做增量计数；收藏是**需要长期保存、能列出清单**的（「我的收藏」要展示记录），放 MySQL 关系表，用唯一约束防重复。评论则用双字段巧妙支撑楼中楼，一次 `root_id IN (...)` 批量查出所有回复，避免逐条查询。

## 功能清单

| 功能 | 说明 | 涉及接口/组件 |
| ---- | ---- | ---- |
| 点赞/取消点赞 | Redis Set 存用户、INCR/DECR 计数，30 天 TTL | `POST /api/video/{id}/like`，`VideoServiceImpl.toggleLike()` |
| 收藏/取消收藏 | 数据库关系表 + 唯一约束去重，SQL 原子自增计数 | `POST /api/video/{id}/favorite`，`toggleFavorite()` |
| 投币 | 每人每天最多 3 枚，单次 1~2 枚，记录落表 | `POST /api/video/{id}/coin`，`coin()` |
| 评论分页 | 一级评论分页 + 楼中楼回复一次性批量组装 | `GET /api/video/{id}/comments`，`comments()` |
| 发表评论/回复 | parent_id=0 一级评论，否则楼中楼回复；触发通知 | `POST /api/video/{id}/comment`，`addComment()` |
| 互动通知 | 点赞/收藏/投币/评论/回复通知（自己不通知自己） | `NotificationService.notify()`，`NotificationType` |
| 我的收藏/历史 | 个人中心清单（收藏/历史时间倒序，视频已删自动跳过） | `GET /api/user/me/favorites`、`/history` |

## 涉及数据表

**`video_comment` 评论表**（楼中楼设计）：

| 字段 | 类型 | 作用 |
| ---- | ---- | ---- |
| id | BIGINT 自增 | 主键 |
| video_id / user_id | BIGINT | 所属视频、评论用户 |
| content | VARCHAR(500) | 评论内容 |
| parent_id | BIGINT，默认 0 | 回复的目标评论 ID；0 = 一级评论 |
| root_id | BIGINT，默认 0 | 所属一级评论 ID（一级评论的 root_id 就是自己） |
| create_time | DATETIME | 评论时间 |

建表要点：`INDEX idx_video_root (video_id, root_id)` 精确命中「查某视频某楼下的所有回复」；`INDEX idx_user (user_id)` 支撑「我的评论」。

**`video_favorite` 收藏表**：`video_id` + `user_id` + `create_time`，`UNIQUE KEY uk_video_user (video_id, user_id)` 保证同一用户不能重复收藏。

**`video_coin` 投币表**：`video_id` + `user_id` + `coin`（每次 1~2 枚）+ `create_time`，`INDEX idx_user (user_id, create_time)` 支撑「今日已投枚数」（Redis key 丢失时以数据库存量重建额度，`SUM(coin)` 聚合）。

关联表：**`watch_history`**（观看历史，同一用户同一视频只留一条）；**`user_notification`**（站内通知，`type` 1点赞 2收藏 3投币 4评论 5回复 6关注，`idx_user_read (user_id, is_read)` 支撑未读红点）。

## 后端实现

所有互动接口集中在 `VideoController`，都先调用 `currentUserId()` 取登录用户（未登录会被 Security 拦截返回 401），然后进 `VideoServiceImpl`。互动前统一用 `requirePublished()` 校验「视频存在且已发布」——对待审核/驳回/下架的视频不能互动。

### 1. 点赞：Redis Set 去重 + 计数

`toggleLike()` 用两个 key：`video:like:{id}`（Set，存点赞用户 ID，去重 + 查状态）和 `video:like:count:{id}`（计数增量）。点赞 `SADD + INCR`，取消 `SREM + DECR`；每次写操作刷新 Set 的 30 天 TTL，防止 key 无限膨胀；点赞成功时通知作者：

```java
@Override
public boolean toggleLike(Long videoId, Long userId) {
    requirePublished(videoId);
    // Redis Set 记录"谁点过赞"（去重 + 查状态快）
    String setKey = KEY_LIKE + videoId;
    String countKey = KEY_LIKE_COUNT + videoId;
    String uid = userId.toString();
    boolean liked = Boolean.TRUE.equals(stringRedisTemplate.opsForSet().isMember(setKey, uid));
    if (liked) {
        // 取消点赞：移出集合 + 计数 -1
        stringRedisTemplate.opsForSet().remove(setKey, uid);
        stringRedisTemplate.opsForValue().decrement(countKey);
    } else {
        // 点赞：加入集合 + 计数 +1
        stringRedisTemplate.opsForSet().add(setKey, uid);
        stringRedisTemplate.opsForValue().increment(countKey);
        // 通知视频作者（自己点赞自己的视频不通知）
        notifyOwner(videoId, userId, NotificationType.LIKE, null);
    }
    // 每次写操作都刷新集合过期时间，防止长期无人访问的 key 无限滞留（被删视频的 key 见 deleteVideo）
    stringRedisTemplate.expire(setKey, LIKE_SET_TTL);
    return !liked;   // true=已点赞，false=已取消
}
```

### 2. 收藏：数据库唯一约束去重

`toggleFavorite()` 用 `video_favorite` 关系表：先查「是否已收藏」，没有就 insert（唯一约束兜底防并发重复）+ 计数 +1 + 通知作者；已收藏就 delete + 计数 -1。计数更新走 `changeVideoCount()` 的 **SQL 原子自增**（`favorite_count = favorite_count + 1`），避免「先查后改」在并发下互相覆盖：

```java
@Override
@Transactional(rollbackFor = Exception.class)
public boolean toggleFavorite(Long videoId, Long userId) {
    requirePublished(videoId);
    // 收藏用数据库关系表（唯一约束天然防重复），计数直接更新库
    VideoFavorite exist = favoriteMapper.selectOne(new LambdaQueryWrapper<VideoFavorite>()
            .eq(VideoFavorite::getVideoId, videoId)
            .eq(VideoFavorite::getUserId, userId));
    if (exist == null) {
        VideoFavorite f = new VideoFavorite();
        f.setVideoId(videoId);
        f.setUserId(userId);
        favoriteMapper.insert(f);
        changeVideoCount(videoId, "favorite_count", 1);
        // 通知视频作者（自己收藏自己的视频不通知）
        notifyOwner(videoId, userId, NotificationType.FAVORITE, null);
        return true;
    } else {
        favoriteMapper.deleteById(exist.getId());
        changeVideoCount(videoId, "favorite_count", -1);
        return false;
    }
}

/** 直接更新视频计数：用 SQL 原子自增（count = count + n），避免"先查后改"在并发下互相覆盖 */
private void changeVideoCount(Long videoId, String column, int delta) {
    videoMapper.update(null, new LambdaUpdateWrapper<Video>()
            .eq(Video::getId, videoId)
            .setSql("`" + column + "` = `" + column + "` + (" + delta + ")"));
}
```

### 3. 投币：每日限 3 枚（Redis 原子计数防并发超限）

`coin()` 的规则：单次 1~2 枚；每日限额走 **Redis 原子计数**（`INCRBY`），并发请求按到达顺序抢占额度，天然不存在「先查后插」的竞态超发；通过后记录投币 + 更新视频投币数 + 通知作者，并返回今日剩余可投币数：

```java
@Override
@Transactional(rollbackFor = Exception.class)
public int coin(Long videoId, Long userId, int coin) {
    requirePublished(videoId);
    if (coin < 1 || coin > 2) {
        throw new BusinessException("单次投币数量为 1~2 枚");
    }
    // 每日限额走 Redis 原子计数（并发防线）：
    // INCRBY 是原子操作，并发请求按到达顺序抢占额度，天然不会"先查后插"竞态超发；
    // key 按天隔离（coin:user:{userId}:{yyyyMMdd}），第二天自动换新 key 重新计数
    String key = KEY_COIN_DAILY + userId + ":" + LocalDate.now().format(DateTimeFormatter.BASIC_ISO_DATE);
    ValueOperations<String, String> ops = stringRedisTemplate.opsForValue();
    if (Boolean.FALSE.equals(stringRedisTemplate.hasKey(key))) {
        // Redis 无今日记录（当天首次投，或 key 丢失）：以数据库存量为准重建计数（SUM 枚数），
        // 避免 Redis 被清空后从零计导致当天可投超过 3 枚；setIfAbsent 保证并发下只初始化一次
        Long dbToday = coinMapper.selectTotalCoinsSince(userId, LocalDate.now().atStartOfDay());
        ops.setIfAbsent(key, String.valueOf(dbToday == null ? 0 : dbToday));
        ops.expire(key, COIN_KEY_TTL);
    }
    // 原子累加本次投币数，返回值 = 包含本次的当日累计枚数
    Long total = ops.increment(key, coin);
    if (total > COIN_DAILY_LIMIT) {
        // 超限：把本次递增回滚，保持 key = 实际已投枚数，再拒绝
        ops.decrement(key, coin);
        throw new BusinessException("今日投币已达上限（3 枚），明天再来吧");
    }
    // 记录投币 + 更新视频投币数
    VideoCoin record = new VideoCoin();
    record.setVideoId(videoId);
    record.setUserId(userId);
    record.setCoin(coin);
    coinMapper.insert(record);
    changeVideoCount(videoId, "coin_count", coin);
    // 通知视频作者（自己给自己视频投币不通知）
    notifyOwner(videoId, userId, NotificationType.COIN, null);
    return (int) (COIN_DAILY_LIMIT - total);   // 今日剩余
}
```

**关键设计**：`INCRBY` 是原子自增，两个并发请求同时投币时，Redis 按到达顺序依次 +1，谁先到谁占用额度，**不会出现两个请求都查到「已投 1 枚」然后各自投 2 枚、最终 5 枚**的竞态。key 丢失时（Redis 清空）用数据库存量（`SUM(coin)`，不是 COUNT，因为单条记录可含 1~2 枚）重建当日计数，保证 Redis 失效后限额仍然生效；`setIfAbsent` 保证并发场景下只初始化一次。

### 4. 评论楼中楼：parent_id + root_id 设计

**结构约定**（见 `addComment()` 注释）：一级评论 `parent_id = 0`、`root_id = 自己`；回复 `parent_id = 被回复的评论`、`root_id = 其所属一级评论`（若回复的是一级评论，root_id 就是它自己）。这样**无论回复几层，都能直接定位到所属楼**：

```java
long parent = parentId == null ? 0 : parentId;
// 楼中楼结构说明：
//   一级评论：parent_id=0，root_id=自己；
//   回复：parent_id=被回复评论，root_id=其所属一级评论（若回复的是一级评论，root_id=它自己）
VideoComment parentComment = null;
if (parent != 0) {
    // 先校验"被回复的评论"存在且属于同一视频，再插入（避免插入后回滚的补偿写法）
    parentComment = commentMapper.selectById(parent);
    if (parentComment == null || !videoId.equals(parentComment.getVideoId())) {
        throw new BusinessException("被回复的评论不存在");
    }
}

VideoComment comment = new VideoComment();
comment.setVideoId(videoId);
comment.setUserId(userId);
comment.setContent(content.trim());
comment.setParentId(parent);
commentMapper.insert(comment);

if (parent == 0) {
    comment.setRootId(comment.getId());
    // 一级评论：通知视频作者（自己评论自己的视频不通知）
    notifyOwner(videoId, userId, NotificationType.COMMENT, content);
} else {
    // 回复：root_id 取被回复评论所属的一级评论（若它自己就是一级评论则取它自己）
    comment.setRootId(parentComment.getRootId() == 0 ? parentComment.getId() : parentComment.getRootId());
    // 楼中楼回复：通知被回复的人（自己回复自己不通知，notify 内部过滤）
    notificationService.notify(parentComment.getUserId(), userId, NotificationType.REPLY, videoId, content);
}
commentMapper.updateById(comment);
```

**查询组装**（`comments()`）：一级评论分页（`parent_id = 0`）→ 用 `root_id IN (一级评论 ids)` 一次性查出所有回复 → 按 rootId 分组塞回对应楼。注意一个细节：**一级评论自身的 root_id 等于自己**，会被 `IN` 命中，所以必须额外加 `parent_id <> 0` 过滤，否则一级评论会作为「自己的回复」重复出现：

```java
// 2. 一次性查出所有一级评论下的回复（root_id in 一级id），避免逐条查询
//    注意：一级评论自身的 root_id == 自己 id，会被 root_id in (...) 命中，
//    因此必须额外加 parent_id <> 0 过滤，否则一级评论会作为"自己的回复"重复出现一次
List<Long> rootIds = roots.stream().map(VideoComment::getId).collect(Collectors.toList());
List<VideoComment> replies = commentMapper.selectList(new LambdaQueryWrapper<VideoComment>()
        .eq(VideoComment::getVideoId, videoId)
        .ne(VideoComment::getParentId, 0)
        .in(VideoComment::getRootId, rootIds)
        .orderByAsc(VideoComment::getCreateTime));
// 3. 按 rootId 分组，组装到对应一级评论下
Map<Long, List<VideoComment>> replyMap = replies.stream()
        .collect(Collectors.groupingBy(VideoComment::getRootId));
return rootPage.convert(root -> toCommentVO(root,
        replyMap.getOrDefault(root.getId(), Collections.emptyList())));
```

### 5. 互动通知：NotificationService.notify()

互动触发点通过 `notifyOwner()` 查视频归属、再调 `notificationService.notify()` 落一条通知。`NotificationServiceImpl.notify()` 的规则：**接收者等于触发者（自己互动自己）时静默跳过**；文案按类型拼接（昵称 + 动作 + 视频名 + 评论内容片段，超过 50 字截断）：

```java
@Override
public void notify(Long userId, Long actorId, int type, Long videoId, String extra) {
    // 自己触发自己的行为不通知自己（给自己点赞、评论自己的视频都不打扰）
    if (userId == null || userId.equals(actorId)) {
        return;
    }
    User actor = userMapper.selectById(actorId);
    String nickname = actor == null ? "匿名用户" : actor.getNickname();
    Video video = videoId == null ? null : videoMapper.selectById(videoId);
    String title = video == null ? "" : video.getTitle();

    UserNotification n = new UserNotification();
    n.setUserId(userId);
    n.setActorId(actorId);
    n.setType(type);
    n.setVideoId(videoId);
    n.setContent(buildContent(nickname, type, title, extra));
    n.setIsRead(0);
    notificationMapper.insert(n);
}
```

通知类型常量见 `constant/NotificationType.java`：`LIKE=1 / FAVORITE=2 / COIN=3 / COMMENT=4 / REPLY=5 / FOLLOW=6`。

### 6. 我的收藏 / 观看历史

`myFavorites()` / `myHistory()` 分页查关系表后**逐条联查视频**，作者删稿（视频不存在）的记录自动跳过，避免空指针或脏数据展示；`interactTime` 字段把收藏时间/观看时间带给前端展示。删除历史用「用户 + 视频」双条件定位（一个用户对同一视频只有一条历史）。

## 前端实现

### 1. 互动区按钮（VideoDetail.vue）

详情页互动区三个按钮：点赞/收藏带 `active` 高亮态，投币显示「今日剩余可投币 X 枚」。未登录点击统一 `userStore.loginVisible = true` 弹登录框。点赞/收藏接口返回**最新布尔状态**，前端用它更新高亮并本地 ±1 计数（乐观更新）：

```js
/** 点赞/取消点赞 */
async function onLike() {
  if (!userStore.user) {
    userStore.loginVisible = true
    return
  }
  try {
    const res = await toggleLike(video.value.id)
    liked.value = res.data
    video.value.likeCount += liked.value ? 1 : -1
  } catch (e) {
    errorMsg.value = e.message || '操作失败'
  }
}

/** 投币 */
async function onCoin() {
  if (!userStore.user) {
    userStore.loginVisible = true
    return
  }
  try {
    const res = await coinVideo(video.value.id, 1)
    coinLeft.value = res.data        // 今日剩余可投币数
    video.value.coinCount += 1
  } catch (e) {
    errorMsg.value = e.message || '操作失败'
  }
}
```

### 2. 评论区（VideoDetail.vue）

评论区分「一级评论 + 楼中楼回复」两级渲染：一级评论带「回复」入口，点开后出现回复输入框；发表一级评论传 `parentId: 0`，回复传 `parentId: c.id`（一级评论 id）。发表成功后 `loadComments()` 重新拉取第一页，并本地 +1 评论数：

```js
/** 发表一级评论 */
async function submitComment() {
  const content = commentText.value.trim()
  if (!content) return
  if (!userStore.user) {
    userStore.loginVisible = true
    return
  }
  submitting.value = true
  try {
    await addComment(video.value.id, { content, parentId: 0 })
    commentText.value = ''
    video.value.commentCount = (video.value.commentCount || 0) + 1
    loadComments()
  } catch (e) {
    errorMsg.value = e.message || '评论失败'
  } finally {
    submitting.value = false
  }
}
```

### 3. API 封装（video.js）

`frontend/src/api/video.js` 的互动接口封装：`toggleLike(id)`、`toggleFavorite(id)`、`coinVideo(id, coin=1)`（coin 走 query 参数）、`getComments(videoId, params)`、`addComment(videoId, data)`；个人中心清单走 `getFavorites(params)`、`getHistory(params)`、`deleteHistory(videoId)`。

## 关键设计说明

**1. 点赞为什么用 Redis Set，收藏为什么用数据库表？**

两者业务性质不同：点赞是**高频低价值**的布尔状态，用户不会去翻「我点过哪些赞」的清单，用 Redis Set 存储后：`SISMEMBER` 查状态 O(1)、`SADD/SREM` 天然去重、`INCR` 顺带计数，且**不占数据库空间**；30 天 TTL 到期自动清理。收藏则要**长期保存并支持「我的收藏」清单查询**（还要按收藏时间排序展示），必须落 MySQL 关系表，唯一约束 `uk_video_user` 防重复。对应地，`init.sql` 注释也写明：点赞状态存于 Redis，MySQL 无落库，属设计内约定。

**2. 楼中楼为什么需要 parent_id + root_id 两个字段？**

如果只有 `parent_id`，查「某楼的所有回复」需要递归遍历（回复的回复的回复……），SQL 复杂且性能差；如果只有 `root_id`，又无法知道「回复的是谁」。双字段各司其职：`parent_id` 记录**直接回复目标**（渲染时可显示「回复 @xxx」），`root_id` 记录**所属楼层**（查询时 `root_id IN (...)` 一次捞出整楼回复）。无论回复嵌套几层都只有两种值语义，插入时 3 条规则即可维护，查询只需 1 条 SQL + 内存分组。

**3. 计数为什么用 SQL 原子自增（setSql）而不是先查后改？**

「查出来 → 内存 +1 → 更新回去」在并发下会丢失更新（两个请求都读到 0，都写回 1）。`setSql("favorite_count = favorite_count + 1")` 把自增下推到 MySQL 行锁内原子执行，任何并发下结果都正确。投币/收藏这类低频写操作直接落库没问题；点赞/播放这类高频操作则进一步拆到 Redis INCR（见文档 02 的 CountSyncTask）。

**4. 互动通知的触发规则是怎样的？**

三类规则：一是**不通知自己**——`notify()` 开头 `userId.equals(actorId)` 直接 return（自己给自己点赞、评论自己的视频都不打扰）；二是**分对象**——一级评论通知视频作者（`notifyOwner`），楼中楼回复通知**被回复的人**（`parentComment.getUserId()`）而不是作者；三是**文案落点一致**——`init.sql` 的种子通知数据强调「每条通知都有真实数据落点」，保证用户点通知能看到对应评论/互动，不会「点到空处」。

## 常见问题

**Q1：点赞后立刻取消，计数会变负数吗？**

不会变成负数——`decrement` 与 `increment` 一一对应，且 `toggleLike` 是「先查状态再操作」的切换语义：只有已点赞才会走 remove+decrement，未点赞只会 add+increment，计数增量始终 ≥ 0。落库时 `CountSyncTask` 也是把增量 `play_count + delta` 累加，数据库值不会回退。唯一边界：用户 A 点赞后 30 天 Set 过期，状态重置为未点赞，此时计数增量仍在（30 天内大概率已落库），行为符合预期。

**Q2：投币的「每日 3 枚」在并发下会不会超限？**

不会。限额已改为 **Redis `INCRBY` 原子计数**：并发请求按到达顺序依次占用额度，谁先到谁 +1，不存在「先查后插」竞态。双重保障：① key 丢失时（Redis 清空）以数据库存量（`SUM(coin)`）重建当日计数，Redis 失效后限额仍然生效；② 数据库 `video_coin` 记录本身是账本，投了多少枚始终可核对。唯一剩余边界：`insert` 在 Redis 递增之后，若数据库写入失败导致事务回滚，Redis 会多占一次额度（用户本次少投 1~2 枚）——极低频且不造成超发，属可接受取舍。

**Q3：评论分页时，楼中楼回复会不会被截断或遗漏？**

`comments()` 的回复查询用 `root_id IN (当前页一级评论 ids)`，只查当前页楼层的回复，不做回复的分页——回复随所在楼一起返回（回复多时一次性全带出，练习规模可接受）。跨页的一致性问题：发表新回复后重新拉第一页即可看到；若翻到旧页，已加载的回复不会自动更新，属常见缓存语义。

**Q4：删除视频后互动数据会怎样？**

`deleteVideo()`（见文档 02）会级联删除该视频的评论、收藏、投币、观看历史与关联通知，并清理 Redis 点赞集合与计数 key——保证互动模块不残留孤儿数据。反过来，「我的收藏/历史」列表在视频被删后通过 `videoMapper.selectById` 判空跳过，不会展示指向已删视频的空卡片。
