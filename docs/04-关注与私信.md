# 04 关注与私信

> 配套项目：my13li13li（Spring Boot 3.2 后端 + Vue3 前端）
> 本文档讲解仿 B 站社区的**关注**与**私信（DM）**两大模块：关注/取关、粉丝/关注列表、互关判定，以及私信的双行会话表设计、抖音式单向私信规则、WebSocket 实时推送与前端红点。

---

## 模块简介

关注是社区关系的基石：用户关注 UP 主后，主页/列表展示互关标识，关注动态流（`/api/video/feed`）也依赖 `user_follow` 表；关注成功还会给被关注者发一条站内通知（`NotificationType.FOLLOW`）。

私信是用户间的点对点沟通。本项目实现了两个很有代表性的设计：

1. **双行会话表**：`dm_conversation` 中每对用户存**两行**（A 一行、B 一行），各自记录"自己的未读数"和"自己视角的最后一条摘要"，会话列表与未读总数都只需单表查询；
2. **抖音式单向私信规则**：非互关用户之间，对方回复前只能发一条；互关则不限次。规则由服务端在发送时强校验，前端通过 `/api/dm/permission` 预判禁用输入框。

实时性方面：发送走 HTTP POST（保证事务与规则校验），落库成功后由 `DmWebSocketHandler` 通过 WebSocket 把新消息推给在线接收方；离线用户靠导航栏红点轮询兜底。

## 涉及数据表

### user_follow（用户关注关系表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 主键，自增 |
| follower_id | BIGINT | 关注者（操作方） |
| following_id | BIGINT | 被关注者（UP 主） |
| create_time | DATETIME | 关注时间 |

建表要点：

- `UNIQUE KEY uk_follow (follower_id, following_id)`：**数据库层兜底防重复关注**——即使并发下两个请求同时插入，也只有一个能成功；
- `INDEX idx_following (following_id)`：粉丝列表（按被关注者查）走这个索引；
- 表里只有两列 ID，没有任何冗余的昵称/头像快照——展示时实时联查 `user` 表，避免数据不一致。

### dm_conversation（私信会话表，双行设计）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 主键，自增 |
| user_id | BIGINT | **会话归属者**（这一行是"谁的"会话） |
| peer_id | BIGINT | 对方用户 ID |
| last_message_id | BIGINT | 最后一条消息 ID（冗余，方便排查） |
| last_content | VARCHAR(100) | 最后一条消息摘要（截断 100 字，会话列表展示） |
| last_time | DATETIME | 最后一条消息时间 |
| unread_count | INT | **我未读的对方消息数**（红点角标） |
| create_time / update_time | DATETIME | 创建时间 / 最后活跃时间（列表排序用） |

建表要点：

- `UNIQUE KEY uk_user_peer (user_id, peer_id)`：同一用户对同一对方只有一行会话；
- `INDEX idx_user_time (user_id, update_time)`：会话列表 `WHERE user_id=? ORDER BY update_time DESC` 直接命中索引；
- 注意**没有**整表级的 `(user_id, peer_id)` 双向唯一约束——A 与 B 的关系由两行承载（`(A,B)` 和 `(B,A)`），这正是双行设计。

### dm_message（私信消息流水表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 主键，自增（历史分页与 WS 推送去重都靠它） |
| sender_id / receiver_id | BIGINT | 发送者 / 接收者 |
| content | VARCHAR(500) | 消息内容（纯文本，前端文本插值渲染防 XSS） |
| create_time | DATETIME | 发送时间（数据库默认当前时间） |

建表要点：

- `INDEX idx_sender (sender_id, receiver_id, id)`、`INDEX idx_receiver (receiver_id, sender_id, id)`：分别覆盖"我发给谁"与"谁发给我"的查询（含抖音规则的 pair 双向 OR 查询）；
- 消息表**不存已读状态**——已读是"会话级"概念（进入会话即全部已读），由 `dm_conversation.unread_count` 承载，避免每条消息都维护一个布尔位。

## 后端实现

### 1. 关注 / 取关（FollowServiceImpl.toggleFollow）

核心思想：**关系表有记录 = 已关注，没有 = 未关注**，一次点击做"查 → 有则删 / 无则插"的切换：

```java
@Override
@Transactional(rollbackFor = Exception.class)
public boolean toggleFollow(Long followerId, Long followingId) {
    // 基础校验：不能关注自己、对方必须存在
    if (followerId.equals(followingId)) {
        throw new BusinessException("不能关注自己");
    }
    User target = userMapper.selectById(followingId);
    if (target == null) {
        throw new BusinessException("用户不存在");
    }
    // 查已有关系：有则取关（删关系），无则关注（插关系 + 发通知）
    UserFollow exist = followMapper.selectOne(new LambdaQueryWrapper<UserFollow>()
            .eq(UserFollow::getFollowerId, followerId)
            .eq(UserFollow::getFollowingId, followingId));
    if (exist == null) {
        UserFollow f = new UserFollow();
        f.setFollowerId(followerId);
        f.setFollowingId(followingId);
        followMapper.insert(f);
        // 关注成功：通知被关注者（type=关注）
        notificationService.notify(followingId, followerId, NotificationType.FOLLOW, null, null);
        return true;
    } else {
        followMapper.deleteById(exist.getId());
        return false;
    }
}
```

**互相关注判定**没有引入第三张关系表或复合状态，而是**双向查两次**：

```java
@Override
public boolean isMutualFollowed(Long userA, Long userB) {
    // 互相关注 = A→B 与 B→A 两条关系都存在，两次 selectCount 即可
    return isFollowed(userA, userB) && isFollowed(userB, userA);
}
```

> 这个 `isMutualFollowed` 是私信抖音规则**豁免判定**的核心依赖（见下文），`profile` 接口也用它填充 `mutualFollowed` 字段。

### 2. 用户主页（FollowServiceImpl.profile）

主页是"关注模块"的聚合出口：基础资料 + 三个统计 + 两个关系标识。统计全部用 `selectCount` 实时计算，未做计数冗余：

```java
vo.setVideoCount(videoMapper.selectCount(new LambdaQueryWrapper<Video>()
        .eq(Video::getUserId, targetUserId)
        .eq(Video::getStatus, VideoStatus.PUBLISHED)));   // 他人主页只看已发布
vo.setFollowerCount(followMapper.selectCount(new LambdaQueryWrapper<UserFollow>()
        .eq(UserFollow::getFollowingId, targetUserId)));  // 粉丝数 = 关注了 TA 的记录数
vo.setFollowingCount(followMapper.selectCount(new LambdaQueryWrapper<UserFollow>()
        .eq(UserFollow::getFollowerId, targetUserId)));   // 关注数 = TA 关注别人的记录数
// 当前登录用户是否已关注（未登录不查，返回 null）
vo.setFollowed(currentUserId == null ? null : isFollowed(currentUserId, targetUserId));
```

**粉丝/关注列表的隐私修补**（代码注释里标注的 2026-09-11 修补）：列表返回的 `UserVO` **不设置 phone**——因为粉丝/关注列表是"半公开"数据（游客可访问），任何人通过列表拿到他人手机号属于敏感信息泄露。

### 3. 私信：双行会话表 + 发送链路（DmServiceImpl.sendMessage）

发送是事务方法，一条消息要同时写 **1 行 dm_message + 2 行 dm_conversation**：

```java
@Override
@Transactional(rollbackFor = Exception.class)
public DmMessageVO sendMessage(Long senderId, DmSendDTO dto) {
    // 1. 基础校验：接收者存在、不能发给自己、内容 1~500 字
    // 2. 抖音式权限校验（互关豁免，非互关单条限制）
    checkCanSend(senderId, receiverId);

    // 3. 消息落库
    DmMessage msg = new DmMessage();
    msg.setSenderId(senderId);
    msg.setReceiverId(receiverId);
    msg.setContent(content);
    messageMapper.insert(msg);

    // 4. 维护发送方的会话行（自己发的消息当然已读，unread_count 不变）
    upsertConversation(senderId, receiverId, msg, now, 0);
    // 5. 维护接收方的会话行（未读 +1）
    upsertConversation(receiverId, senderId, msg, now, 1);
    ...
}
```

`upsertConversation` 的语义：**存在则更新摘要/时间/未读数增量；不存在则插入**（注意"未读数增量"参数：`0`=自己发的，`1`=对方发来的）：

```java
private void upsertConversation(Long owner, Long peer, DmMessage msg, LocalDateTime time, int unreadDelta) {
    DmConversation conv = conversationMapper.selectOne(new LambdaQueryWrapper<DmConversation>()
            .eq(DmConversation::getUserId, owner)
            .eq(DmConversation::getPeerId, peer));
    // 摘要截断 100 字，对应表字段 VARCHAR(100)
    String summary = msg.getContent().length() > SUMMARY_MAX_LEN
            ? msg.getContent().substring(0, SUMMARY_MAX_LEN) : msg.getContent();
    if (conv == null) {
        conv = new DmConversation();
        // ... 设置 lastMessageId/lastContent/lastTime/unreadCount=unreadDelta 后 insert
    } else {
        conv.setLastMessageId(msg.getId());
        conv.setLastContent(summary);
        conv.setLastTime(time);
        conv.setUpdateTime(time);
        if (unreadDelta > 0) {
            conv.setUnreadCount((conv.getUnreadCount() == null ? 0 : conv.getUnreadCount()) + unreadDelta);
        }
        conversationMapper.updateById(conv);
    }
}
```

### 4. 抖音式单向私信规则（checkCanSend + permission）

规则：**互相关注 → 不限次；非互关 → 最后一条消息必须是"对方发给我的"才允许发**。服务端发送时强校验（`checkCanSend`，拒绝抛异常），同时提供不抛异常的 `permission` 给前端预判：

```java
private void checkCanSend(Long senderId, Long receiverId) {
    if (followService.isMutualFollowed(senderId, receiverId)) {
        return; // 互关不限次
    }
    DmMessage last = lastMessageOf(senderId, receiverId);
    if (last != null && last.getSenderId().equals(senderId)) {
        // 非互关 + 最后一条是我发的（对方未回复）→ 拒绝
        throw new BusinessException("对方回复你之前只能发送一条私信");
    }
}
```

`lastMessageOf` 用**双向 OR 条件**查 pair 的最近一条消息（避免把"我发给 A 的"和"A 发给我的"各查一次再比较时间）：

```java
private DmMessage lastMessageOf(Long userA, Long userB) {
    return messageMapper.selectOne(new LambdaQueryWrapper<DmMessage>()
            .and(w -> w
                    .and(w2 -> w2.eq(DmMessage::getSenderId, userA).eq(DmMessage::getReceiverId, userB))
                    .or(w2 -> w2.eq(DmMessage::getSenderId, userB).eq(DmMessage::getReceiverId, userA)))
            .orderByDesc(DmMessage::getId)
            .last("LIMIT 1"));
}
```

这个实现**天然覆盖了"发一条 → 等回复 → 对方回了 → 又能发一条"的滑动语义**：只要对方回复过，最后一条的发送者就变成对方，规则自动放行，无需额外状态字段。

### 5. WebSocket 实时推送

**① 握手鉴权（JwtHandshakeInterceptor）**：浏览器的 `new WebSocket(url)` 无法自定义请求头，token 只能拼在 URL 上（`ws://host/ws?token=xxx`）。而 `SecurityConfig` 已对 `/ws/**` permitAll（JwtAuthenticationFilter 读不到 query 参数），所以鉴权唯一入口就在握手拦截器里：

```java
@Override
public boolean beforeHandshake(ServerHttpRequest request, ServerHttpResponse response,
                               WebSocketHandler wsHandler, Map<String, Object> attributes) {
    // 从 query 里解析 token 参数（用 UriComponentsBuilder，不手写 split）
    String token = UriComponentsBuilder.fromUri(request.getURI()).build()
            .getQueryParams().getFirst("token");
    if (token == null || token.isBlank()) {
        response.setStatusCode(HttpStatus.UNAUTHORIZED);
        return false;  // 拒绝握手
    }
    try {
        // 解析 token 拿用户 id（subject），并确认账号仍然存在且可用
        Claims claims = jwtUtils.parseToken(token);
        Long userId = Long.valueOf(claims.getSubject());
        LoginUser loginUser = (LoginUser) userDetailsService.loadUserById(userId);
        // 握手通过：userId 存入 attributes 供 Handler 使用
        attributes.put("userId", loginUser.getId());
        return true;
    } catch (Exception e) {
        response.setStatusCode(HttpStatus.UNAUTHORIZED);
        return false;  // token 无效/过期/用户不存在
    }
}
```

**② 在线用户映射（DmWebSocketHandler）**：用 `ConcurrentHashMap<Long, WebSocketSession>` 维护"用户 → 连接"，采用**后者覆盖前者**策略（同用户新连接建立时主动关闭旧连接），断开时只有"映射里存的还是这个连接"才移除，防止旧连接回调误删新连接：

```java
// 在线用户映射：userId → 连接（后者覆盖前者）
private static final Map<Long, WebSocketSession> SESSIONS = new ConcurrentHashMap<>();

@Override
public void afterConnectionEstablished(WebSocketSession session) {
    Long userId = (Long) session.getAttributes().get("userId");
    // 后者覆盖前者：同用户新连接顶掉旧连接
    WebSocketSession old = SESSIONS.put(userId, session);
    if (old != null && old != session && old.isOpen()) {
        closeQuietly(old);
    }
}

@Override
protected void handleTextMessage(WebSocketSession session, TextMessage message) {
    // 心跳：PING → PONG（前端每 25s 发一次，防止代理掐掉空闲连接）
    if (PING.equals(message.getPayload())) {
        sendText(session, PONG);
    }
}

/** 给指定在线用户推送 JSON（新私信 DM_NEW）——尽力而为，失败只记日志 */
public void sendToUser(Long userId, Object payload) {
    WebSocketSession session = SESSIONS.get(userId);
    if (session == null || !session.isOpen()) return; // 不在线，正常情况
    try {
        sendText(session, objectMapper.writeValueAsString(payload));
    } catch (Exception e) {
        log.warn("推送 WebSocket 消息给用户 {} 失败：{}", userId, e.getMessage());
    }
}
```

> 注意 `objectMapper` 是**注入 Spring 容器的实例**而非 `new ObjectMapper()`——前者注册了 JavaTimeModule，能序列化 VO 里的 `LocalDateTime`；裸 new 的实例遇到 `createTime` 会抛 "Java 8 date/time type not supported" 导致推送静默失败（代码注释里明确记录了此坑）。

**③ 先落库、后推送（DmController.send）**：Controller 在事务方法 `sendMessage` **成功返回后**再调 `dmWebSocketHandler.sendToUser`——保证"先落库、后推送"，推送失败也不影响消息持久化：

```java
@PostMapping("/api/dm/send")
public Result<DmMessageVO> send(@RequestBody DmSendDTO dto) {
    DmMessageVO vo = dmService.sendMessage(currentUserId(), dto);
    // 事务已提交（sendMessage 返回），再推送——接收方不在线则静默跳过，靠红点轮询兜底
    dmWebSocketHandler.sendToUser(vo.getReceiverId(),
            Map.of("type", "DM_NEW", "data", vo));
    return Result.success(vo);
}
```

### 消息页（frontend/src/views/Message.vue）

页面是"左会话列表 + 右聊天窗"布局，核心难点是**双通道消息去重**：同一消息可能同时来自 HTTP 历史拉取和 WS 推送，用 `msgIds`（Set）按 id 去重：

```js
// 双通道去重：HTTP 历史 + WS 推送都按 id 记到这里，防止同一消息渲染两次
const msgIds = new Set()

/** 收到新私信推送(WS) */
function onDmNew(vo) {
  // 列表里找到这条会话；没有则造一条（第一次私聊就收到回复的场景）
  let conv = conversations.value.find(c => c.peerId === vo.senderId)
  if (!conv) {
    conv = { peerId: vo.senderId, peerNickname: `用户${vo.senderId}`, ... }
    conversations.value.unshift(conv)
  }
  conv.lastContent = vo.content
  conv.lastTime = vo.createTime

  if (activePeer.value && activePeer.value.peerId === vo.senderId) {
    appendMessage(vo)      // 正在跟这个人聊 → 上屏（带去重）
    markRead(vo.senderId)  // 正在看 → 直接已读
    conv.unreadCount = 0
    refreshPermission()    // 对方回复了 → 解锁我的输入框
  } else {
    conv.unreadCount = (conv.unreadCount || 0) + 1
    messageStore.dmUnread++ // 全局红点增量修正（NavBar 轮询的权威值会周期性对齐）
  }
}
```

WebSocket 连接带**指数退避重连 + 25s 心跳**：

```js
let reconnectDelay = 1000 // 重连退避：1s 起，每次翻倍，封顶 30s
let wsClosedByMe = false  // 组件卸载主动断开时不重连

function connectWs() {
  const token = getToken()
  if (!token) return
  const proto = location.protocol === 'https:' ? 'wss' : 'ws'
  ws = new WebSocket(`${proto}://${location.host}/ws?token=${token}`)
  ws.onmessage = (e) => {
    if (e.data === 'PONG') return   // 心跳回包直接忽略
    const msg = JSON.parse(e.data)
    if (msg.type === 'DM_NEW') onDmNew(msg.data)
  }
  ws.onclose = () => {
    stopHeartbeat()
    if (!wsClosedByMe) {
      setTimeout(connectWs, reconnectDelay)
      reconnectDelay = Math.min(reconnectDelay * 2, 30000)
    }
  }
}
```

## 关键设计说明

**① 为什么私信用"双行会话表"而不是一张"关系行 + 两个未读数"？**
假设用单行设计（一行为一对用户，含 `unreadA`、`unreadB` 两个未读列），那"我的会话列表"需要 `WHERE peer 涉及我` 才能查到行，且两个人都要更新同一行（并发写冲突、行锁竞争）；而双行设计下，"我的会话列表"就是 `SELECT * FROM dm_conversation WHERE user_id=我 ORDER BY update_time DESC` 的单表查询，未读总数就是 `SUM(unread_count)`，天然支持两个人**各自独立、互不阻塞**地更新自己的那一行。代价是发一条消息要写两行（写放大），练习项目完全可接受（`DmServiceImpl` 与 `dm_conversation` 表的注释都明确记录了该权衡）。

**② 抖音式"非互关只能发一条"为什么靠"最后一条消息是谁发的"判定，而不是单独加状态字段？**
加"是否已回复"字段需要在一个字段上同时表达"有没有发过/对方回没回/我又发了没"等多个状态，容易出现状态组合爆炸。而"最后一条消息的 sender"这一事实本身就蕴含了滑动语义：不存在（搭讪第一条）→ 可发；最后一条是对方的（对方回复过）→ 可发；最后一条是我发的（对方还没回）→ 拒绝。对方回复后规则自动解锁，**无需任何额外字段和状态机**。

**③ 为什么推送放在 Controller 而不是事务方法里？**
`sendMessage` 是 `@Transactional` 方法。如果推送写在事务内，WebSocket I/O 失败会**污染数据库事务**（导致消息发送整体回滚或长时间占用事务）；而"先落库（事务提交）→ 再推送"可以保证：消息持久化是可靠的，推送只是"尽力而为"——接收方不在线时静默跳过，靠红点轮询兜底，数据不会丢。

**④ WebSocket 为什么用原生 TextWebSocketHandler 而不是 STOMP？**
本项目的 WS 唯一用途是"服务端 → 客户端"的新私信推送（点对点单一路径）。STOMP 的订阅/消息代理模型属于过度设计；原生 handler 更直观，心跳、连接映射、重复连接策略都可显式控制，教学也更清晰（`WebSocketConfig` 注释原文）。

## 常见问题

**Q1：私信页面收到了重复消息（HTTP 历史里一条、WS 推送一条）？**
这是双通道的预期行为，Message.vue 用 `msgIds`（Set）按消息 id 去重：`appendMessage` 先查 `msgIds.has(vo.id)`，已有则直接 return。历史分页加载时同样先过滤 `records.filter(m => !msgIds.has(m.id))`，兼容"WS 先到、历史后到"的时序。

**Q2：为什么我给非互关用户发了一条后就发不出去了？**
这是抖音式规则的预期：非互关时"对方回复你之前只能发送一条私信"。服务端 `checkCanSend` 与前端 `/api/dm/permission` 双重保障——前端禁用输入框并显示提示条，即使绕过前端直接调接口，服务端也会抛 `BusinessException` 拒绝。对方回复后规则自动解锁。

**Q3：用户不在线时发的私信会丢吗？**
不会。WebSocket 推送只是"尽力而为"：消息在事务中已落库到 `dm_message`，并更新了接收方的 `dm_conversation` 行（unread_count +1）。接收方上线后：会话列表能看到新摘要，NavBar 30s 轮询 `getDmUnreadTotal` 会拉到红点数字；打开聊天窗时历史接口也能拉到消息。

**Q4：同一个人开两个浏览器标签页，WebSocket 会怎样？**
采用"后者覆盖前者"策略：新连接建立时 `SESSIONS.put` 顶掉旧连接并主动关闭它，保证在线映射里始终只有一个活跃连接（单浏览器练习场景的最简策略）。旧连接的 `afterConnectionClosed` 回调即使晚到，也会因"当前映射里存的不是这个连接"而跳过移除，不会误删新连接。
