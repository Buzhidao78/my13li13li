# 订单分页功能从 0 到 1 开发指南

> 配套练习：会员订单功能（《会员订单功能从0到1开发指南.md》）
> 本文档讲解"订单列表分页"功能（MyBatis-Plus 分页插件 + 前端翻页控件）如何从 0 到 1 写出来：
> **先写什么、后写什么、为什么这个顺序**，前后端代码全部覆盖。

---

## 0. 功能总览：为什么需要分页？

**业务故事**：会员订单越攒越多，如果一次性把用户所有订单都查出来返回给前端，会有什么问题？

| 问题 | 通俗解释 |
|---|---|
| 性能 | 用户有 1000 单，一次查 1000 条，数据库累、网络慢、页面卡 |
| 体验 | 一次性铺一长串，想找一条历史订单得滚很久 |
| 规范 | 大厂接口普遍是"分页返回"约定（records + total） |

**分页的本质就两件事：**

- 后端：`LIMIT offset, size` 只查一页 + `COUNT(*)` 统计总条数
- 前端：记住"现在第几页"，点翻页就重新请求那一页

**技术落点：**

- 后端用 MyBatis-Plus 的**分页插件**（一个拦截器，自动拼 `LIMIT` 和 `COUNT`，我们一行 SQL 都不用写）
- 前端用 Vue3 的 `ref` / `computed` 维护分页状态

一句话记住：**分页 = 后端只返回"一页"数据 + 前端告诉后端"要第几页"**。

---

## 1. 第 0 步：先想清楚"分页数据长什么样"（接口契约）

写任何代码之前，先想清楚**前端需要后端返回什么**。分页接口的通用"契约"（所有主流框架都长这样）：

```
GET /api/order/my?page=1&size=5

{
  "records": [...],   // 当前页的数据列表
  "total": 6,         // 总条数（算总页数要用）
  "current": 1,       // 当前是第几页
  "pages": 2          // 总页数
}
```

> **为什么先定接口契约？** 前端要什么、后端给什么，先对齐，两边的代码才好写。这个契约和 MyBatis-Plus 的 `IPage` 结构**完全一致**——所以后端直接返回 `IPage` 就行，不用自己拼 JSON。

## 2. 后端开发顺序（核心思想：按"依赖倒序"）

```
① 分页插件配置        MybatisPlusConfig（地基）
② Service 接口        OrderService.listMyOrders(userId, page, size)
③ Service 实现        OrderServiceImpl（selectPage + convert）
④ 控制器              OrderController（接收 page/size）
⑤ 待支付接口          getPendingOrder（分页引出的新问题）
```

### 第 1 步：分页插件配置（地基中的地基）

**为什么排第一？** MyBatis-Plus 默认的 `selectList` 会一次性查出所有数据，**只有注册了分页插件，`selectPage` 才会自动生成 `LIMIT` 和 `COUNT`**。没有这个插件，后面的代码全白写。

```java
/**
 * MyBatis-Plus 配置：注册分页插件
 */
@Configuration
public class MybatisPlusConfig {

    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        // 分页插件：告诉 MyBatis-Plus "数据库是 MySQL"
        interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));
        return interceptor;
    }
}
```

> **类比**：分页插件像"万能翻译器"。你只写"我要第 2 页，每页 5 条"，它自动翻译成 MySQL 能懂的 `LIMIT 5, 5` 和 `SELECT COUNT(*)`。没装翻译器，你说人话它听不懂。

**怎么验证它生效了？** 调用分页方法后，控制台打印的 SQL 里出现 `LIMIT` 和 `SELECT COUNT(*)`，就说明插件在工作。

---

### 第 2 步：Service 接口（定义"要什么"）

**为什么先写接口？** 接口是"契约"，告诉实现类"你必须提供这个能力"。先定接口，实现类照着写，也方便上层（Controller）先用起来。

```java
/**
 * 分页查询当前用户的所有订单（按创建时间倒序）
 * 返回 IPage<MemberOrderVO>：records=当前页数据，total=总条数
 */
IPage<MemberOrderVO> listMyOrders(Long userId, long page, long size);
```

三个参数想清楚：

- `userId`：只查**当前用户**的订单（绝对不能查所有人的）
- `page`：第几页（从 1 开始）
- `size`：每页几条

> **为什么返回 `IPage` 而不是 `Page`？** 这是 MyBatis-Plus 的 API 约定：`Page.convert()` 返回的是 `IPage` 接口类型。用接口类型做返回，实现更灵活（详见后面"踩坑 1"）。

---

### 第 3 步：Service 实现（核心中的核心）

```java
@Override
public IPage<MemberOrderVO> listMyOrders(Long userId, long page, long size) {
    // 1. selectPage：第一个参数是"页码+每页条数"，第二个是查询条件
    Page<MemberOrder> p = orderMapper.selectPage(new Page<>(page, size),
            new LambdaQueryWrapper<MemberOrder>()
                    .eq(MemberOrder::getUserId, userId)        // 只看自己的订单
                    .orderByDesc(MemberOrder::getCreateTime)); // 新的在前
    // 2. convert：把实体(MemberOrder)列表转成 VO(MemberOrderVO)列表
    return p.convert(MemberOrderVO::from);
}
```

**拆开看这两行：**

- `new Page<>(page, size)`：分页"凭证"，告诉插件要第几页、每页几条
- `.eq(userId)`：安全过滤，只查当前用户的（**防越权**）
- `.orderByDesc(createTime)`：按创建时间倒序，最新订单在最上面
- `selectPage` 返回 `Page<MemberOrder>`，里面已经有 `records`（当前页数据）和 `total`（总条数）了
- `convert(MemberOrderVO::from)`：把**实体**转成**前端能看的 VO**（把 status 翻译成 statusText 等），返回新的 `IPage`，`records` 已转换，`total` 不变

> **为什么把"实体转 VO"放在 Service 里而不是 Controller？** VO 是"业务出参"的概念，属于业务层职责。Controller 只负责转发，不该有转换逻辑。这和"DTO/VO 分层"的规矩一致。

---

### 第 4 步：控制器（接收分页参数）

```java
/**
 * 分页查询当前用户的订单列表（倒序）
 * 返回 IPage<MemberOrderVO>：records=当前页数据，total=总条数
 */
@GetMapping("/my")
public Result<IPage<MemberOrderVO>> myOrders(
        @RequestParam(defaultValue = "1") long page,   // 没传就默认第 1 页
        @RequestParam(defaultValue = "5") long size) { // 没传就默认每页 5 条
    return Result.success(orderService.listMyOrders(currentUserId(), page, size));
}
```

- `@RequestParam`：从 URL 问号后面拿参数，如 `/api/order/my?page=2&size=5`
- `defaultValue`：用户不传参数时给默认值，**防止 page 为 null 报错**
- `currentUserId()`：从登录态取当前用户，**绝不信任前端传的 userId**

> **为什么控制器最后写？** 控制器是"最上层"，只负责把 HTTP 参数接进来、转发给 Service。Service 写好了，控制器就是几行"接线工"代码。

---

### 第 5 步：待支付订单接口（分页引出的新问题）

**为什么分页后还要多写一个接口？** 想一想：订单分页后，"我的订单"表格每页只显示 5 条。如果用户有一笔**待支付**订单在第 3 页，他在第 1 页就找不到"模拟支付"按钮了——**待支付订单会被"埋"在后面的页里**。

解法：单独写一个接口，专门查"最新的待支付订单"，页面顶部永远有"继续支付"入口，不受分页影响。

```java
// ===== Service 接口 =====
/**
 * 查询当前用户最新的"待支付"订单（没有则返回 null）
 * 用于页面顶部展示"继续支付"入口：无论订单列表翻到第几页，待支付订单都能被找到
 */
MemberOrderVO getPendingOrder(Long userId);

// ===== Service 实现 =====
@Override
public MemberOrderVO getPendingOrder(Long userId) {
    // 查最新一条"待支付"订单，没有返回 null
    MemberOrder order = orderMapper.selectOne(new LambdaQueryWrapper<MemberOrder>()
            .eq(MemberOrder::getUserId, userId)            // 只看当前用户
            .eq(MemberOrder::getStatus, 0)                 // 只要"待支付"的
            .orderByDesc(MemberOrder::getCreateTime)       // 最新的
            .last("LIMIT 1"));                             // 只要 1 条
    return order == null ? null : MemberOrderVO.from(order);
}

// ===== 控制器 =====
@GetMapping("/pending")
public Result<MemberOrderVO> pending() {
    return Result.success(orderService.getPendingOrder(currentUserId()));
}
```

> **设计思想**：分页是为了"列表浏览"，但"待支付订单"是**业务状态**（用户必须处理它），所以要单独暴露，不能被分页"淹没"。这就像银行 App：流水列表分页，但"待还款账单"永远置顶。

## 3. 前端开发顺序

后端接口齐了，前端把接口"接"到页面上。顺序同样按依赖：

```
① API 封装          api/order.js 加分页参数
② 页面状态          Recharge.vue 加 page/pageSize/total/totalPages
③ 加载逻辑          loadAll 传分页参数
④ 翻页 UI           上一页/下一页按钮
```

### 第 1 步：API 封装（接口带分页参数）

```js
/** 分页查询当前用户的订单列表：page 从 1 开始，size 每页条数 */
export function getMyOrders(page = 1, size = 5) {
  return request.get('/order/my', { params: { page, size } })
}

/** 查询当前用户最新的"待支付"订单（无则返回 null），用于页面顶部"继续支付"入口 */
export function getPendingOrder() {
  return request.get('/order/pending')
}
```

> **为什么先封装 API？** 页面组件不关心 URL 长什么样，只调用 `getMyOrders(page, size)`。将来接口参数变了，只改这一个文件，页面零改动。参数带默认值（`page = 1, size = 5`），调用处不传也不会报错。

---

### 第 2 步：页面状态（分页的"记忆"）

分页本质是"记住现在第几页"，所以要用 `ref` 存起来：

```js
// 分页状态：当前页码、每页条数、总条数
const page = ref(1)
const pageSize = ref(5)
const total = ref(0)

// 总页数：至少 1 页（total 为 0 时也显示"第 1 页"，避免除零/空白）
const totalPages = computed(() => Math.max(1, Math.ceil(total.value / pageSize.value)))
```

> **为什么要用 `computed` 算总页数？** 总页数 = 总条数 ÷ 每页条数（向上取整）。它是从 `total` 和 `pageSize` **推导**出来的，不需要单独存一份。数据一变，`totalPages` 自动跟着变——这就是"派生状态"用 `computed` 的意义。

---

### 第 3 步：加载逻辑（请求当前页数据）

```js
/** 加载页面数据：等级列表 + 会员信息 + 待支付订单 + 当前页订单列表 */
async function loadAll() {
  // 四个请求并行（Promise.all），一次刷新全部数据
  const [lv, info, pending, list] = await Promise.all([
    getMemberLevels(),
    getMemberInfo(),
    getPendingOrder(),                       // 待支付订单单独查（不受分页影响）
    getMyOrders(page.value, pageSize.value)  // 订单列表带分页参数
  ])
  levels.value = lv.data
  if (lv.data.length) selectedLevel.value = lv.data[0].level
  memberInfo.value = info.data
  currentOrder.value = pending.data          // 顶部"继续支付"入口
  // 分页结果：records 是当前页数据，total 是总条数（翻页按钮靠它算总页数）
  orders.value = list.data.records
  total.value = list.data.total
}

/** 翻页：切到指定页并重新加载 */
function changePage(p) {
  // 边界保护：页码不能小于 1、不能超过总页数、不能和当前页相同
  if (p < 1 || p > totalPages.value || p === page.value) return
  page.value = p
  loadAll()
}
```

> **为什么待支付订单要放进 `Promise.all`？** 它和列表是**两件独立的事**：待支付订单是"置顶入口"，列表是"当前页数据"。一起并行请求，一次刷新搞定，互不干扰。
> **为什么翻页要边界保护？** 防止用户把页码"点穿"（第 0 页、超过总页数），也防止重复加载同一页。前端先拦住，后端兜底。

---

### 第 4 步：翻页 UI（分页条）

```html
<!-- 分页条：只有有数据（total>0）才显示 -->
<div v-if="total > 0" class="pagination">
  <button class="page-btn" :disabled="page <= 1" @click="changePage(page - 1)">上一页</button>
  <span class="page-info">第 {{ page }} / {{ totalPages }} 页，共 {{ total }} 条</span>
  <button class="page-btn" :disabled="page >= totalPages" @click="changePage(page + 1)">下一页</button>
</div>
```

- `v-if="total > 0"`：没有数据时不显示分页条（避免"第 1 / 1 页，共 0 条"的尴尬）
- `:disabled="page <= 1"`：第 1 页时"上一页"禁用（没有更早的了）
- `:disabled="page >= totalPages"`：最后一页时"下一页"禁用
- `changePage(page ± 1)`：切页后自动重新加载对应页数据

## 5. 踩坑记录（今天实际遇到的真问题）

### 坑 1：编译报错 —— `Page.convert()` 返回的是 `IPage`，不是 `Page`

- **现象**：`listMyOrders` 里写 `return p.convert(MemberOrderVO::from)`，编译报错 `Type mismatch: cannot convert from IPage<MemberOrderVO> to Page<MemberOrderVO>`。
- **根因**：MyBatis-Plus 的 `Page.convert()` 方法签名返回的是**接口类型** `IPage<R>`，不是实现类 `Page<R>`。方法声明的返回类型是 `Page`，返回值是 `IPage`，编译自然不通过。
- **解决**：把接口、实现类、控制器的返回类型**统一改成 `IPage<MemberOrderVO>`**。返回结构（records/total/current/pages）完全一样，前端无感知。
- **教训**：MyBatis-Plus 的 `Page`（实现类）和 `IPage`（接口）返回值**混用**容易踩坑。记住多态的思想：**对外用接口类型**（`IPage`），具体实现（`Page`）留在方法内部。

### 坑 2：只改后端、忘记前端传参，翻页永远返回同一页

- **现象**：前端调用 `getMyOrders()` 不带 `page/size`，后端走 `defaultValue`（永远第 1 页），点"下一页"没反应。
- **根因**：前后端参数没对上——后端要 `page/size`，前端没传。
- **解决**：前端 API 封装带上 `page/size` 参数，翻页时用当前 `page` 重新请求。
- **教训**：**前后端参数名必须完全一致**（`page`/`size`）。这类问题排查先看浏览器 Network 里请求 URL 的 query 参数对不对。

## 7. 进阶方向（练完这些再往深处走）

1. **页码控件升级**：当前只有"上一页/下一页"。进阶：像真实网站那样加**数字页码**（1 2 3…）、快速跳页输入框、"首页/末页"按钮，中间用"…"省略。
2. **搜索 + 分页组合**：分页往往和筛选条件一起用（按状态筛选、按时间范围）。进阶：筛选条件也作为查询参数传给后端，`page` 变化时保持筛选条件不变。
3. **总数优化**：`COUNT(*)` 在大数据量下也慢。进阶：了解 MySQL `COUNT` 优化、或考虑用缓存记录订单总数（注意一致性）。
4. **无限滚动**：移动端 App 常用"下拉加载更多"代替分页按钮。进阶：用滚动事件 + 追加 `records` 实现（后端接口不用改，前端逻辑不同）。
5. **排序稳定性**：如果创建时间相同，分页可能"串页"。进阶：`ORDER BY create_time DESC, id DESC`，加一个唯一字段保证排序稳定。

---

## 8. 一句话总结

**分页功能的核心原则同样是"按依赖倒序"：**

- 后端：**先配分页插件**（没有它 `selectPage` 不工作）→ Service 接口 → Service 实现 → Controller。后端只要"会算一页 + 会数总数"。
- 前端：**先封装带参 API** → 加分页状态 → 请求时带上页码 → 画分页条。前端只要"记住第几页 + 点一下重新请求"。

**分页带来的设计问题**：待支付订单会被"埋"进后面的页，所以单独加一个 `/order/pending` 接口，保证关键业务状态永远能被找到。

> **记住一句话**：分页不是"把数据切碎"，而是**后端只查一页 + 前端记住页号**。`LIMIT` 决定"查多少"，`total` 决定"有几页"。
