# 登录功能从 0 到 1 —— 全栈开发教学指南

> 配套项目：practice2（Vue3 + Spring Boot 3.2 全栈练习）
> 本指南带你走一遍"登录系统"从无到有的完整过程：先看懂大局，再按依赖顺序逐层搭建，最后用一条真实请求把前后端串起来。

***

## 0. 先看懂大局：登录功能到底在做什么？

### 0.1 一个生活类比：小区门禁系统

把整个登录系统想象成一个小区的**门禁保安系统**：

| 现实世界            | 代码世界                               |
| --------------- | ---------------------------------- |
| 住户登记信息（姓名、电话）   | `user` 表（存用户）                      |
| 住户把密码登记在物业的保险箱里 | BCrypt 加密后存数据库                     |
| 物业给你发一张**门禁卡**  | 后端签发 **JWT token**                 |
| 你刷卡进门，保安刷卡验真    | 前端每次请求带上 token                     |
| 门口那台"验卡机"       | `JwtAuthenticationFilter`（每请求都执行）  |
| 门禁的"允许进入规则表"    | `SecurityConfig`（哪些门能进、哪些要卡）       |
| 保安按卡号查住户信息      | `UserDetailsServiceImpl`（按 id 查用户） |
| 临时访客的**一次性纸条**  | Redis 里的短信验证码（5 分钟作废）              |

一句话总结：**注册 = 住户登记 + 领卡；登录 = 出示凭证 + 保安放行；之后的请求 = 刷卡进出各栋楼**。

### 0.2 整体架构图

```
┌────────────────────────── 前端（Vue3） ──────────────────────────┐
│  NavBar（登录按钮）→ LoginModal（登录弹窗）                        │
│        │                                                         │
│        │  axios（自动带 token，401 自动弹登录框）                    │
└────────┼─────────────────────────────────────────────────────────┘
         ▼
┌────────────────────────── 后端（Spring Boot） ───────────────────┐
│  AuthController（接口入口）                                       │
│    → AuthService（业务逻辑）                                      │
│        ├─ BCrypt 加密/校验密码                                    │
│        ├─ Redis 存/校验验证码                                     │
│        └─ JwtUtils 签发 token                                    │
│  SecurityConfig（访问规则总开关）                                  │
│    → JwtAuthenticationFilter（每请求验 token）                    │
│    → UserDetailsServiceImpl（查用户）→ UserMapper → MySQL        │
└──────────────────────────────────────────────────────────────────┘
```

### 0.3 本功能涉及的核心知识点

1. **Spring Security**：Spring 官方安全框架，负责"认证（你是谁）"和"授权（你能干什么）"
2. **JWT**：一种无状态的令牌，用户登录后拿到它，后续请求带上它即可，服务器不需要记 session
3. **BCrypt**：一种**单向**哈希算法，只能加密不能解密，密码存库安全
4. **Redis**：内存数据库，用来存"一次性验证码"（天然支持过期时间）
5. **MyBatis-Plus**：操作数据库（我们已经会了）

## 1. 第一步：数据库 —— 先有"户口本"

**为什么先做数据库？** 后端所有代码都是在"读写数据"，没有表，后面的代码就是空中楼阁。这是全栈开发的第一性原则：**数据先行**。

### 1.1 建表脚本 [schema.sql](backend/src/main/resources/db/schema.sql)

```sql
CREATE TABLE IF NOT EXISTS `user` (
    id          BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
    username    VARCHAR(50)           DEFAULT NULL COMMENT '用户名（账号密码登录用，可空）',
    password    VARCHAR(100)          DEFAULT NULL COMMENT '密码（BCrypt 加密）',
    phone       VARCHAR(20)           DEFAULT NULL COMMENT '手机号（验证码登录用）',
    nickname    VARCHAR(50)           DEFAULT NULL COMMENT '昵称',
    avatar      VARCHAR(255)          DEFAULT NULL COMMENT '头像地址',
    gender      TINYINT               DEFAULT 0 COMMENT '性别 0-未知 1-男 2-女',
    sign        VARCHAR(100)          DEFAULT NULL COMMENT '个性签名',
    status      TINYINT      NOT NULL DEFAULT 0 COMMENT '账号状态 0-正常 1-禁用',
    deleted     TINYINT      NOT NULL DEFAULT 0 COMMENT '逻辑删除 0-正常 1-删除',
    create_time DATETIME              DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    update_time DATETIME              DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (id),
    UNIQUE KEY uk_username (username),
    UNIQUE KEY uk_phone (phone)
) ENGINE = InnoDB COMMENT = '用户表';
```

### 1.2 为什么这样设计？三个关键决策

| 设计                               | 为什么                                   |
| -------------------------------- | ------------------------------------- |
| `password` 允许为空（DEFAULT NULL）    | 因为有两种登录方式：手机号验证码登录的用户**可以不设置密码**，留空即可 |
| `username` 和 `phone` 都加**唯一索引**  | 保证同一账号、同一手机号只能注册一次（业务规则）              |
| `status` 状态字段                    | 管理员可以"禁用"某个账号，登录时校验它（`isEnabled()`）   |
| `deleted` 逻辑删除字段 + `@TableLogic` | 不真正删除数据，防止误删，这是 MyBatis-Plus 的规范做法    |

### 1.3 对应实体 [User.java](backend/src/main/java/com/example/practice/entity/User.java)

```java
@Data                       // Lombok：自动生成 getter/setter
@TableName("user")          // 指定表名
public class User {
    @TableId(type = IdType.AUTO)   // 主键自增
    private Long id;
    private String username;
    private String password;
    private String phone;
    // ... 其余字段一一对应
    @TableLogic              // 逻辑删除，查询时自动加 deleted = 0
    private Integer deleted;
}
```

[Mapper](backend/src/main/java/com/example/practice/mapper/UserMapper.java) 只需要一行：

```java
public interface UserMapper extends BaseMapper<User> {
    // BaseMapper 自带增删改查，不用写 SQL
}
```

> **练习建议**：动手把 user 表 + User 实体 + Mapper 建好，然后用一个接口测通"往表里插一条数据"，再继续往下。

## 2. 后端：从地基到接口（7 个步骤）

### 2.1 第 1 步：配置环境（[pom.xml](backend/pom.xml) + [application.yml](backend/src/main/resources/application.yml)）

**写什么**：引入三个新依赖 + 配置连接信息。

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
<dependency>
    <groupId>io.jsonwebtoken</groupId>
    <artifactId>jjwt-api</artifactId>
    <version>0.12.5</version>
</dependency>
```

```yaml
spring:
  data:
    redis:
      host: localhost
      port: 6379
jwt:
  secret: practice2-jwt-secret-key-please-change-it-0123456789  # 至少 32 字节
  expire: 604800000   # token 有效期 7 天（毫秒）
```

**为什么先做这个？** 依赖是代码的"地基"——你要用哪个库，得先把它引进来。否则写了代码也无法编译运行。JWT 的 `secret` 单独放配置文件，是为了安全和好维护（改配置不用改代码）。

### 2.2 第 2 步：统一返回 + 全局异常（地基中的地基）

**写什么**：[Result.java](backend/src/main/java/com/example/practice/common/Result.java)、[BusinessException.java](backend/src/main/java/com/example/practice/common/BusinessException.java)、[GlobalExceptionHandler.java](backend/src/main/java/com/example/practice/common/GlobalExceptionHandler.java)

**为什么？** 前后端约定一个**统一的返回格式**，前端只需要解析一种结构：

```java
// 所有接口都返回这个结构：code=200 成功，非 200 失败
{ "code": 200, "message": "success", "data": { ... } }
```

再配合 `BusinessException`（业务错误）+ `GlobalExceptionHandler`（统一拦截），**业务代码里只需要** **`throw new BusinessException("用户名已存在")`**，错误就会自动转成标准 JSON，不用在每个方法里手动 return 错误。

### 2.3 第 3 步：JWT 身份证工厂（[JwtUtils.java](backend/src/main/java/com/example/practice/util/JwtUtils.java)）

**写什么**：生成 token、解析 token 两个方法。

**为什么单独写一个工具类？** JWT 的生成和解析是**通用能力**，登录用、过滤器用，所以抽成独立工具类，职责单一，其它地方调用即可。

核心代码：

```java
public String createToken(Long userId, String username) {
    return Jwts.builder()
            .subject(String.valueOf(userId))   // 用户 id 放 subject
            .claim("username", username)       // 用户名作为附加信息
            .expiration(new Date(System.currentTimeMillis() + expire))
            .signWith(key())                   // 用 secret 签名防篡改
            .compact();
}
```

**类比**：JWT 就是一张身份证——里面有"持有者信息（id、用户名）+ 有效期 + 防伪签名"。因为签名用的是服务器才知道的 `secret`，别人伪造就会验签失败。

### 2.4 第 4 步：Spring Security 骨架（整个系统最核心的 4 个文件）

按依赖关系写：

**(a)** **[LoginUser.java](backend/src/main/java/com/example/practice/security/LoginUser.java)** —— 让 Spring Security 认识我们的用户

```java
// 实现 UserDetails 接口，Spring Security 才能调用 isEnabled() 等判断
public class LoginUser implements UserDetails {
    private Long id;
    private String username;
    private String password;
    private Integer status;
    // ...
    @Override
    public boolean isEnabled() { return status != null && status == 0; }  // 禁用账号不能登录
}
```

**(b)** **[UserDetailsServiceImpl.java](backend/src/main/java/com/example/practice/security/UserDetailsServiceImpl.java)** —— "查户口的人"

```java
@Override
public UserDetails loadUserByUsername(String username) {
    User user = userMapper.selectOne(...);   // 按用户名查数据库
    return new LoginUser(user);
}

public UserDetails loadUserById(Long userId) {   // 按 id 查（JWT 过滤器用）
    return new LoginUser(userMapper.selectById(userId));
}
```

**(c)** **[JwtAuthenticationFilter.java](backend/src/main/java/com/example/practice/config/JwtAuthenticationFilter.java)** —— "门口验卡机"

```java
// 每个请求都会经过这个过滤器
protected void doFilterInternal(...) {
    String token = 从请求头 Authorization 取出;
    if (token != null) {
        Long userId = jwtUtils.parseToken(token).getSubject();  // 验签 + 取 id
        UserDetails user = userDetailsService.loadUserById(userId);  // 查用户
        if (user.isEnabled()) {
            // 校验通过 → 把用户信息放进 SecurityContext（相当于"放行并标记是谁"）
            SecurityContextHolder.getContext().setAuthentication(authentication);
        }
    }
    chain.doFilter(request, response);  // 继续走后续流程
}
```

**(d)** **[SecurityConfig.java](backend/src/main/java/com/example/practice/config/SecurityConfig.java)** —— "门禁总规则表"，把上面全串起来

```java
http.csrf(disable)               // 前后端分离 + JWT 无状态，关闭 CSRF
    .sessionManagement(STATELESS) // 不用 session，全靠 token
    .authorizeHttpRequests(auth -> auth
        .requestMatchers("/api/auth/**").permitAll()   // 登录注册放行
        .requestMatchers("/api/user/hello").permitAll()// 测试接口放行
        .anyRequest().authenticated())                 // 其余都要登录
    .exceptionHandling(e -> e
        .authenticationEntryPoint(restAuthenticationEntryPoint)  // 401
        .accessDeniedHandler(restAccessDeniedHandler))           // 403
    .addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class);
```

**为什么过滤器是"串起来"的关键？** 这三个角色配合：

- `SecurityConfig` 决定"哪些门要卡、哪些不用"
- `JwtAuthenticationFilter` 负责"验卡"（在真正到达接口前执行）
- 验卡通过的信息放进 `SecurityContext`，接口里随时能拿到当前用户

**为什么放 401/403 处理器？** 注意：Spring Security 在**进入 Controller 之前**就拦截了，所以全局异常处理器（`@RestControllerAdvice`）管不到这里。必须自己写两个处理器，返回统一格式的 JSON：

```java
// 未登录 → 401
response.setStatus(401);
response.getWriter().write(objectMapper.writeValueAsString(Result.error(401, "未登录或登录已过期")));
```

### 2.5 第 5 步：参数和返回结构（[dto/](backend/src/main/java/com/example/practice/dto) + [vo/](backend/src/main/java/com/example/practice/vo)）

**写什么**：注册、登录的入参（DTO），返回给前端的数据（VO）。

```java
// 入参：前端发什么，后端收什么
public class RegisterDTO {
    private String username;
    private String password;
    private String phone;
    private String code;   // 手机验证码
    private String nickname;
}

public class LoginDTO {
    private String username;
    private String password;
}

// 出参：登录成功后返回 token + 用户信息
public class LoginVO {
    private String token;
    private UserVO user;
}

public class UserVO {   // 只暴露需要的信息，绝不含密码！
    private Long id;
    private String username;
    private String nickname;
    private String avatar;
    private String phone;
}
```

**为什么把"密码"排除在 UserVO 外？** 这是安全习惯：**永远不要把密码字段返回给前端**。用一个专门的"视图对象"来控制暴露哪些字段，比直接返回实体安全得多。

### 2.6 第 6 步：业务逻辑（[AuthService.java](backend/src/main/java/com/example/practice/service/AuthService.java) + [AuthServiceImpl.java](backend/src/main/java/com/example/practice/service/impl/AuthServiceImpl.java)）

**写什么**：注册、账号密码登录、手机号验证码登录、发送验证码。这是**整个功能的大脑**。

先定义接口（先定"要做什么"），再写实现（再想"怎么做"）：

```java
public interface AuthService {
    void register(RegisterDTO dto);
    LoginVO login(LoginDTO dto);              // 账号密码
    LoginVO loginByPhone(PhoneLoginDTO dto);  // 手机号验证码
    void sendCode(String phone);
}
```

实现类关键逻辑（每个方法都有清晰注释）：

```java
/** 注册：校验唯一性 + BCrypt 加密 */
public void register(RegisterDTO dto) {
    // 1. 校验用户名、手机号是否已被注册（查数据库）
    // 2. 校验验证码（复用 verifyCode）
    // 3. passwordEncoder.encode(密码) → BCrypt 加密后才入库！
    // 4. 保存用户
}

/** 账号密码登录：完全交给 Spring Security 校验 */
public LoginVO login(LoginDTO dto) {
    // 核心就一行：
    Authentication auth = authenticationManager.authenticate(
            new UsernamePasswordAuthenticationToken(dto.getUsername(), dto.getPassword()));
    // Spring Security 内部自动完成：查用户 + BCrypt 比对
    // 校验通过 → 用 JwtUtils 签发 token 返回
}

/** 发送验证码：存 Redis，带过期和防刷 */
public void sendCode(String phone) {
    // 1. 防重复发送：60 秒内不能再次发送（Redis 里有 key 就拒绝）
    // 2. 生成 6 位随机数字
    // 3. 存入 Redis：sms:code:{phone}，有效期 5 分钟
    // 4. 练习环境：打印到控制台（生产环境接短信平台）
}
```

**为什么"账号密码登录"只有一行核心代码？** 这就是 Spring Security 的价值——它把"查用户、比密码、抛异常"这套繁琐流程封装好了，我们只需要把参数交给 `AuthenticationManager`，它内部自动调用 `UserDetailsService` + `PasswordEncoder` 完成校验。

**为什么手机号验证码登录"不走" Spring Security？** 因为验证码登录没有密码，校验的是"验证码对不对"。所以我们在业务层自己校验 Redis 里的验证码，查用户后**复用同一个 JwtUtils 签发 token**。这样两种登录方式殊途同归。

### 2.7 第 7 步：控制器（[AuthController.java](backend/src/main/java/com/example/practice/controller/AuthController.java)）

**写什么**：把 Service 方法暴露成 HTTP 接口，这是**最薄的一层**（只做参数接收和返回）。

```java
@RestController
@RequestMapping("/api/auth")   // 这些接口在 SecurityConfig 里已放行
public class AuthController {
    @Autowired
    private AuthService authService;

    @PostMapping("/register")   public Result<Void> register(@RequestBody RegisterDTO dto) {...}
    @PostMapping("/login")      public Result<LoginVO> login(@RequestBody LoginDTO dto) {...}
    @PostMapping("/login/phone")public Result<LoginVO> loginByPhone(@RequestBody PhoneLoginDTO dto) {...}
    @PostMapping("/code")       public Result<Void> sendCode(@RequestBody SendCodeDTO dto) {...}
}
```

**为什么 Controller 要这么薄？** 分层架构的核心思想：**Controller 只负责"接客"（收请求、返回结果），业务都下沉到 Service**。这样 Controller 很干净，Service 可以复用、可以测试。

### 2.8 后端编写顺序总结（为什么这样排）

写代码的顺序 = **依赖关系的倒序**：先写"别人依赖我"的，再写"我依赖别人"的。

```
① schema.sql（数据库）
② User 实体 + Mapper（数据模型）
③ pom.xml + application.yml（依赖与配置）
④ Result + 异常处理（统一返回，几乎所有类都依赖）
⑤ JwtUtils（工具类）
⑥ LoginUser → UserDetailsServiceImpl（Spring Security 的用户模型）
⑦ JwtAuthenticationFilter（过滤器）
⑧ 401/403 处理器（异常出口）
⑨ SecurityConfig（把 ⑥⑦⑧ 串起来的总开关）
⑩ DTO / VO（参数与返回结构）
⑪ AuthService 接口 + 实现（业务逻辑，依赖上面所有）
⑫ AuthController（最后暴露接口）
```

**一句话：数据 → 配置 → 地基 → 工具 → 安全框架 → 参数 → 业务 → 接口。**

### **一、 核心类/接口清单及作用解析**

这套系统由 11 个核心类/接口组成，按照职责可以划分为四个层次：

#### **1. 统一响应与异常处理层**

- **`Result<T>`**：统一响应封装类。它的作用是强制规定所有接口返回给前端的 JSON 格式（包含 `code`, `message`, `data`），保证前后端交互数据结构的绝对一致性。
- **`BusinessException`**：自定义业务异常类。继承自 `RuntimeException`，用于在业务逻辑不满足时（如参数校验失败、账号被禁用）主动抛出。它携带了自定义的 `code` 和 `message`。
- **`GlobalExceptionHandler`**：全局异常处理器。通过 `@RestControllerAdvice` 拦截所有未被 `try-catch` 捕获的异常。它负责将 `BusinessException` 或 Spring Security 抛出的异常统一转换为 `Result` 格式返回，防止向前端暴露底层报错堆栈。

#### **2. Spring Security 安全鉴权层**

- **`LoginUser`**：安全用户实体类。实现了 Spring Security 的 `UserDetails` 接口。它的作用是作为“安全通行证”，将数据库中的普通 `User` 实体转化为 Spring Security 能够识别的格式，并提供账号状态检查（如 `isEnabled()`）。
- **`UserDetailsServiceImpl`**：用户数据加载服务。实现了 `UserDetailsService` 接口。它的作用是提供从数据库加载用户数据的标准方法，包括按用户名查询（`loadUserByUsername`）和按 ID 查询（`loadUserById`），供 Security 框架在登录和鉴权时调用。
- **`JwtAuthenticationFilter`**：JWT 认证过滤器。继承自 `OncePerRequestFilter`。它的作用是拦截每一个 HTTP 请求，从请求头中提取 Token，解析验签，查库确认账号状态，并将合法的用户信息注入到当前线程的 `SecurityContextHolder` 中。
- **`SecurityConfig`**：安全核心配置类。通过 `@EnableWebSecurity` 开启安全框架。它的作用是定义全局安全规则：关闭 CSRF、配置无状态 Session、设置接口放行/拦截规则、注册 JWT 过滤器，以及配置 401/403 的统一 JSON 异常处理。

#### **3. 认证业务逻辑层**

- **`AuthService`**：认证服务接口。定义了注册、账号密码登录、手机号验证码登录、发送验证码等核心业务方法的契约。
- **`AuthServiceImpl`**：认证服务实现类。承载了所有认证相关的核心业务逻辑，包括 Redis 验证码的存取与防刷、密码的 BCrypt 加密比对、调用 Spring Security 的 `AuthenticationManager` 进行登录校验，以及 JWT Token 的生成。

#### **4. 接口暴露层**

- **`AuthController`**：认证控制器。作为 HTTP 入口，接收前端的 JSON 请求，调用 `AuthService` 处理业务，并将结果包装为 `Result` 返回。它不包含任何业务逻辑，保持极度轻量。

  <br />

### **二、 账号密码登录完整流程深度解析**

以用户发起 **账号密码登录 (`POST /api/auth/login`)** 为例，整个系统的数据流转和代码执行过程如下：

**1. 请求接入与参数绑定**

- 前端发送带有 `username` 和 `password` 的 JSON 请求。
- `AuthController` 的 `login()` 方法通过 `@RequestBody` 接收并反序列化为 `LoginDTO` 对象，随后调用 `authService.login(dto)`。

**2. 触发 Spring Security 认证机制**

- `AuthServiceImpl.login()` 将 `LoginDTO` 中的账号密码封装为 `UsernamePasswordAuthenticationToken` 对象。
- 代码调用 `authenticationManager.authenticate(authenticationToken)`，将认证请求正式移交给 Spring Security 框架。

**3. 数据库查询与密码比对 (Security 内部执行)**

- Spring Security 自动调用 `UserDetailsServiceImpl.loadUserByUsername(username)`。
- 该方法使用 MyBatis-Plus 的 `LambdaQueryWrapper` 从 MySQL 中查询用户。若查不到，抛出 `UsernameNotFoundException`；若查到，将 `User` 实体转换为 `LoginUser` 返回。
- Spring Security 拿到 `LoginUser` 后，自动调用 `BCryptPasswordEncoder` 将前端传来的明文密码与数据库中的密文进行比对。
- 同时，Security 会检查 `LoginUser.isEnabled()` 等方法，确认账号是否处于正常可用状态。

**4. 异常拦截与统一返回 (若认证失败)**

- 如果密码错误或账号被禁用，Spring Security 会抛出 `BadCredentialsException` 或 `DisabledException`。
- 异常向上抛出，被 `GlobalExceptionHandler` 捕获。
- 全局异常处理器将异常转换为 `Result.error("用户名或密码错误")`，直接返回给前端，Controller 层的后续代码不再执行。

**5. Token 签发与成功返回 (若认证成功)**

- 如果密码正确且账号正常，`authenticationManager.authenticate()` 返回包含 `LoginUser` 的 `Authentication` 对象。
- `AuthServiceImpl` 从中提取出 `LoginUser`，调用 `JwtUtils.createToken()` 生成 JWT Token。
- 将 Token 和用户基本信息封装为 `LoginVO` 返回给 Controller。
- `AuthController` 最终将其包装为 `Result.success(loginVO)`，以 `{code: 200, message: "success", data: {token: "...", user: {...}}}` 的格式返回给前端。

这就是这套登录系统从代码定义到实际运行的完整闭环。

## 3. 前端：从入口到界面（5 个步骤）

前端是"脸面"，逻辑相对后端简单，核心是**登录态管理**和**接口封装**。

### 3.1 第 1 步：登录态管理（[store/user.js](frontend/src/store/user.js)）

**写什么**：把 token 和用户信息存在 `localStorage`，用 Vue 的 `reactive` 做成全局响应式状态。

**为什么？** 登录状态是**全站共享**的——导航栏要显示头像、axios 要带 token、401 要弹登录框，处处都要访问它。用一个全局 store 统一管理，任何组件都能读取和修改：

```js
export const userStore = reactive({
  user: JSON.parse(localStorage.getItem('practice2_user')) || null,  // 刷新不丢
  loginVisible: false   // 是否显示登录弹窗（全局控制）
})

export function getToken() { return localStorage.getItem('practice2_token') }
export function setToken(token) { localStorage.setItem('practice2_token', token) }
export function setUser(user) { userStore.user = user; localStorage.setItem('practice2_user', JSON.stringify(user)) }
export function clearAuth() { /* 退出登录：清空 token 和用户 */ }
```

**为什么用 localStorage？** 刷新页面后登录状态不能丢，而 localStorage 是持久化的。用 `reactive` 包裹后，`userStore.user` 一变，所有组件自动更新（响应式）。

### 3.2 第 2 步：axios 封装（[api/request.js](frontend/src/api/request.js)）

**写什么**：统一 axios 实例，做两件全局的事。

```js
// 1. 请求拦截器：每个请求自动带上 token
request.interceptors.request.use((config) => {
  const token = getToken()
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

// 2. 响应拦截器：解包 Result + 遇到 401 自动弹登录框
request.interceptors.response.use(
  (response) => {
    const res = response.data
    if (res.code === 200) return res          // 成功 → 直接给 data
    return Promise.reject(new Error(res.message))  // 业务失败 → 抛错
  },
  (error) => {
    if (error.response?.status === 401) {      // 登录过期
      clearAuth()
      userStore.loginVisible = true            // 自动弹出登录框
    }
    return Promise.reject(error)
  }
)
```

**为什么值得单独封装？** 如果不封装，每个接口都要手动写"取 token、塞 header、解包、判断 401"，重复代码爆炸。封装后，业务代码只需一行：`const res = await login({...})`。

### 3.3 第 3 步：导航栏（[NavBar.vue](frontend/src/components/NavBar.vue)）

**写什么**：B站风格的顶部导航栏，右侧根据登录态二选一。

```vue
<!-- 未登录：显示登录按钮 -->
<button v-if="!userStore.user" class="login-btn" @click="userStore.loginVisible = true">登录</button>

<!-- 已登录：显示头像 + 昵称 + 退出 -->
<div v-else class="user-area">
  <img :src="userStore.user.avatar" class="avatar" />
  <span>{{ userStore.user.nickname }}</span>
  <button @click="handleLogout">退出</button>
</div>
```

**为什么用** **`userStore.user`** **判断登录态？** 因为它是响应式的——登录成功后 `setUser()` 一改，导航栏自动从"登录按钮"变成"头像昵称"，**不需要手动刷新或跳转**，这就是响应式的威力。

### 3.4 第 4 步：登录弹窗（[LoginModal.vue](frontend/src/components/LoginModal.vue)）

**写什么**：三个 Tab 的登录弹窗（密码登录 / 验证码登录 / 注册），这是前端最复杂的组件。

关键逻辑：

```js
// 密码登录：调后端接口，成功就保存登录态
async function handlePwdLogin() {
  const res = await login({ username, password })
  setToken(res.data.token)      // 保存 token
  setUser(res.data.user)        // 保存用户 → 导航栏自动更新
  close()                       // 关闭弹窗
}

// 验证码登录：带 60 秒倒计时
async function handleSendCode() {
  await sendCode(phone)         // 练习环境验证码打印在后端控制台
  countdown.value = 60          // 开始倒计时，禁用按钮
  timer = setInterval(() => countdown.value--, 1000)
}
```

**为什么成功后的处理就这么三步？** 因为登录态管理的逻辑都在 store 里封装好了，这里只管"调用接口 + 保存结果"，职责清晰。

### 3.5 第 5 步：首页（[Home.vue](frontend/src/views/Home.vue)）

**写什么**：B站风格视频卡片网格（练习阶段用假数据），把 NavBar 和 LoginModal 挂到全局。

```vue
<!-- App.vue：全局布局 -->
<template>
  <NavBar />                <!-- 导航栏全局展示 -->
  <router-view />           <!-- 页面内容 -->
  <LoginModal v-if="userStore.loginVisible" />  <!-- 登录弹窗全局控制 -->
</template>
```

### 3.6 前端编写顺序总结

```
① store/user.js（登录态地基）
② api/request.js（请求封装，依赖 ①）
③ api/auth.js（具体接口）
④ NavBar.vue（登录按钮入口）
⑤ LoginModal.vue（登录逻辑）
⑥ App.vue / Home.vue（组装）
```

**前端一句话：先管好"登录状态"，再封装"请求"，最后做"界面"。**

## 5. 这个练习里踩过的坑（经验教训）

1. **坑 1：手机号注册的用户没有用户名**
   - 现象：验证码登录拿到的 token，访问接口却 401
   - 原因：token 里存了 `username=null`，过滤器按用户名查不到用户
   - 解决：**JWT 的 subject 用用户 id，过滤器按 id 查用户**（id 永远存在且唯一）
   - 教训：**主键（id）才是身份的稳定标识，别拿可空的业务字段当身份**
2. **坑 2：后端改了代码但没生效**
   - 现象：接口返回 500 "系统繁忙"
   - 原因：8080 上跑的是旧进程（改代码前启动的，JVM 已加载旧 class）
   - 解决：**改完 Java 代码必须重启后端**
   - 教训：怀疑"代码没生效"时，先重启进程，再看日志堆栈
3. **坑 3：Spring Security 的 401/403 不走全局异常处理器**
   - 原因：Security 过滤器在进入 Controller 之前就拦截了
   - 解决：自己写 `AuthenticationEntryPoint`（401）和 `AccessDeniedHandler`（403）
   - 教训：**框架的"外层"异常要由框架自己的处理器接管**
4. **坑 4：密码不能明文存储**
   - 错误：`user.setPassword(dto.getPassword())`
   - 正确：`user.setPassword(passwordEncoder.encode(dto.getPassword()))`
   - 教训：**BCrypt 是单向哈希，只加密、不能解密**，这是存密码的铁律
5. **坑 5：验证码要一次性、要防刷**
   - 校验成功后立即删除（`verifyCode` 里 `delete`）
   - 60 秒防重复发送（Redis 里记一个短期的 key）
   - 教训：**验证码是最容易被攻击的地方，过期 + 一次性 + 限频缺一不可**
